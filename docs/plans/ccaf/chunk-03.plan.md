### 1. Coordinator prompt: fixed checks to adaptive coverage
- Key concepts: narrow coordinator; fixed checklist; general screening angles; gap identification; specialized screening agent; final synthesis; human review of generated output.
- Exam-relevant facts: course contrasts a coordinator that always applies three prescribed checks with one that generates initial angles, asks which stakeholder perspectives or dimensions are missing, adds only gaps, delegates, then synthesizes; identical spoke prompt means coordinator prompt is variable under comparison (3683-3845). More output does not establish correctness; compare against sample data and human judgement (3846-3900).
- Candidate objectives: `ccaf-cTBD-o1` Draft: distinguish fixed task decomposition from coordinator-directed gap coverage; `ccaf-cTBD-o2` Draft: identify why output quality needs evaluation against representative examples.
- Glossary terms with g- slugs: `g-narrow-coordinator`; `g-fixed-checklist`; `g-screening-angle`; `g-gap-coverage`; `g-synthesis`; `g-representative-data`.
- Diagram candidates with archetype: `comparison` fixed-checklist coordinator versus gap-covering coordinator; `process` coordinator -> specialized screening calls -> synthesis; `callout` same spoke prompt, changed coordinator prompt.
- Comparison/decision table candidates with rows and columns: columns `Approach`, `How angles arise`, `Gap check`, `Observed output`, `Validation need`; rows `Narrow coordinator`, `Gap-covering coordinator`.
- MCQ candidates (count + applied stem ideas): 3. A hiring coordinator has three static checks but misses stakeholder concerns: choose prompt change; same screening tool yields broader report after coordinator change: identify changed layer; team sees richer output: choose required next validation action.
- Recall prompts (count + prompts): 3. What distinguishes fixed checks from gap coverage? Which prompt is held constant in course comparison? Why does a broader report not prove better judgement?
- Confusion pairs with discriminator: fixed decomposition vs adaptive coverage - first executes preselected checks, second identifies missing relevant dimensions; output volume vs output validity - more detail is not evidence without evaluation.
- Common wrong turn misconceptions: "A coordinator must always split work into separate hard-coded agents" -> course shows one specialized agent can be contextually directed for multiple angles; "Generated output is validated because it looks more complete" -> validate with examples and human judgement.
- Causal step chains only if genuine: initial screening angles -> inspect missing perspectives/dimensions -> add only gaps -> delegate specialized screening -> synthesize report.

### 2. Dynamic selection

Course prompt guidance says adapt to observed information and never invoke a screening agent unless it answers a real question; dynamically generated angles need not be the same each run (4040-4185). Instructor advises hand-design for real use and warns garbage in produces garbage out (3961-4005).
- Candidate objectives: `ccaf-cTBD-o3` Draft: select when a coordinator should conditionally invoke a specialist; `ccaf-cTBD-o4` Draft: explain resource and relevance risks of applying every pipeline mechanically.
- Glossary terms with g- slugs: `g-dynamic-selection`; `g-dynamic-routing`; `g-spoke`; `g-conditional-invocation`; `g-routing-guidance`; `g-mechanical-pipeline`; `g-token-consumption`.
- Diagram candidates with archetype: `decision` request evidence -> needed screening angle? -> invoke or skip specialist; `comparison` full fixed pipeline versus dynamically selected calls; `worked-scenario` strong technical match, factual match, and non-traditional background routing examples named by course (4040-4070).
- Comparison/decision table candidates with rows and columns: columns `Observed request condition`, `Question still unanswered`, `Route or skip`, `Why`; rows `Simple factual match`, `Strong technical match`, `Non-traditional background`, `No real question`.
- MCQ candidates (count + applied stem ideas): 3. Candidate directly matches a required fact: choose unnecessary scan to skip; coordinator generates an angle solely because it is on a static list: identify routing flaw; team wants lower unnecessary usage: choose decision criterion.
- Recall prompts (count + prompts): 3. What does dynamic selection optimize in this example? State routing test before invoking an agent. Why are generated angles not necessarily a prewritten list?
- Confusion pairs with discriminator: dynamic selection vs static checklist - former decides per observed case, latter runs predefined checks; skip vs failure - skip is deliberate because no real question exists, failure is unsuccessful attempted work.

### 3. Research partitioning
- Key concepts: overlapping research; distinct scope; partition planner; structured JSON; agent; scope; rules; include/exclude boundaries; upstream selection; dumb coordinator; one call per partition.
- Exam-relevant facts: giving multiple researchers same brief yields overlapping answers and wasted tokens; carve distinct slices (4186-4245). Coordinator receives partitions, invokes exactly one screening call per partition, and must not add angles; routing belongs upstream in planner to avoid two decision layers conflicting (4306-4425).
- Candidate objectives: `ccaf-cTBD-o5` Draft: design non-overlapping sub-agent partitions with explicit boundaries; `ccaf-cTBD-o6` Draft: assign routing ownership to one layer when planner and coordinator are separated.
- Glossary terms with g- slugs: `g-research-partitioning`; `g-overlap`; `g-partition-planner`; `g-partition-scope`; `g-partition-rule`; `g-include-exclude-boundary`; `g-routing-ownership`.
- Diagram candidates with archetype: `process` input -> partition planner -> JSON partitions -> one specialist call per partition -> synthesis; `comparison` overlapping duplicate briefs versus distinct partition scopes; `decision` planner creates a partition only if dimension is genuinely needed.
- Comparison/decision table candidates with rows and columns: columns `Design`, `Selection owner`, `Scope overlap risk`, `Coordinator responsibility`, `Expected waste`; rows `All agents same brief`, `Dynamic coordinator only`, `Partition planner plus coordinator`.
- MCQ candidates (count + applied stem ideas): 4. ### 4. Refinement loop
- Key concepts: one-shot output; evaluation coverage; refinement iteration; identified gap; bounded retries; final recommendation; coverage score; dataset-based evaluation.
- Exam-relevant facts: refinement differs from one-shot work by feeding evaluation back into the loop (4426-4470). Course example permits up to four refinement iterations, evaluates coverage after all initial partition agents report, re-delegates only identified gaps if coverage is insufficient, and submits final only after evaluation permits it (4471-4540). Observed score movement alone did not prove value; instructor calls for larger datasets and testing (4541-4590).
- Candidate objectives: `ccaf-cTBD-o7` Draft: sequence coverage evaluation, bounded gap refinement, and finalization; `ccaf-cTBD-o8` Draft: distinguish a loop completion condition from an unsupported quality claim.
- Glossary terms with g- slugs: `g-refinement-loop`; `g-one-shot`; `g-coverage-evaluation`; `g-coverage-score`; `g-identified-gap`; `g-iteration-limit`; `g-finalization-gate`.
- Diagram candidates with archetype: `process` initial partitions -> coverage evaluation -> sufficient? -> final or gap-only delegation -> repeat within limit; `decision` coverage sufficient versus insufficient; `callout` maximum four iterations in demonstrated coordinator prompt.
- Comparison/decision table candidates with rows and columns: columns `Stage`, `Input`, `Allowed action`, `Exit condition`, `Prohibited action`; rows `Initial screening`, `Coverage evaluation`, `Refinement`, `Final submission`.
- MCQ candidates (count + applied stem ideas): 3. Coverage evaluator finds missing code-quality evidence: choose next action; coordinator submits before coverage check: identify control failure; repeated refinement has no bound: choose missing guardrail.
- Recall prompts (count + prompts): 3. What triggers refinement? What work is re-delegated? What must occur before final submission?
- Confusion pairs with discriminator: refinement loop vs repeat whole pipeline - loop fills identified gaps only; coverage score vs validated quality - score guides process but needs empirical evaluation.

### 5. Coordinator observability and control
- Key concepts: observable coordinator layer; structured logging; timestamp; log level; token count; latency; request ID; persistent audit trail; context control; scoped partition; spoke isolation; coverage gate; error handling.
- Exam-relevant facts: print-only output is weak observability; course lists absent error handling, API tracing, token counts, latency, request IDs, persistent records, stored spoke responses, and partition-to-question records (4591-4705). Every spoke receiving full job/resume context is loose control; scope is advisory unless enforced at spoke level (4706-4755). Proposed fixes include structured logs, JSON error handling, persisted inputs/outputs, mid-run coverage evaluation, explicit final gate, and scoped agent rules (4756-4860). Course says robust validation should include staged adversarial/context-pollution tests and output logs may need a log directory (4861-4915).
- Candidate objectives: `ccaf-cTBD-o9` Draft: identify observability data needed to audit coordinator execution; `ccaf-cTBD-o10` Draft: distinguish prompt-advisory partition scope from enforced spoke-level scope; `ccaf-cTBD-o11` Draft: place explicit coverage and finalization controls in a coordinator workflow.
- Glossary terms with g- slugs: `g-coordinator-observability`; `g-structured-logging`; `g-request-id`; `g-latency`; `g-audit-trail`; `g-context-control`; `g-spoke-isolation`; `g-scope-enforcement`; `g-mid-run-gap-detection`.
- Diagram candidates with archetype: `diagram` coordinator observability boundary showing traces, scoped calls, responses, coverage evaluator, and final gate; `comparison` print-only output versus structured persistent audit trail; `process` agent report -> coverage evaluation -> finalization gate; `callout` one-direction coordinator-to-spoke communication noted as a positive isolation property.
- Comparison/decision table candidates with rows and columns: columns `Control area`, `Observed weakness`, `Course-proposed control`, `Evidence captured`; rows `Logging`, `Errors`, `Message capture`, `Context scope`, `Coverage`, `Final submission`.
- MCQ candidates (count + applied stem ideas): 4. Production coordinator cannot explain a recommendation: choose missing audit records; partition scope exists only in coordinator JSON but spoke can answer any question: identify enforcement gap; a spoke fails silently: choose error-control improvement; recommendation issued before all dimensions covered: choose gate.
- Recall prompts (count + prompts): 4. List three trace fields course names. Why is full context to every spoke loose control? What evidence ties a question to its partition? What makes final submission an explicit gate?
- Confusion pairs with discriminator: logging vs observability - logs are one signal; observability also requires errors, traces, inputs/outputs, and control-state evidence; advisory scope vs enforced scope - first instructs, second validates/rejects out-of-scope work.
- Common wrong turn misconceptions: "Console print statements create an audit trail" -> ephemeral output lacks persistent run evidence; "No cross-spoke messaging proves all context boundaries are correct" -> isolation can coexist with excessive shared input; "A final recommendation implies coverage check ran" -> explicit gating must enforce order.
- Causal step chains only if genuine: scoped partition/question -> spoke call and structured response/error capture -> coverage evaluation -> sufficient coverage gate -> final recommendation; otherwise record gaps/failure and do not finalize.

### 6. Coordinated sub-agent failure handling

- Diagram candidates with archetype: `process` coordinator -> inventory/order/notification agents -> typed reports -> synthesized outcome; `worked-scenario` executive-team notification permission denial and recovery; `callout` each sub-agent sees only its assigned tool.
- Comparison/decision table candidates with rows and columns: columns `Outcome`, `Report status`, `Failure context`, `Coordinator treatment`, `Example`; rows `Successful result`, `Access/permission failure`, `Valid empty/insufficient inventory result`, `Partial result`.
