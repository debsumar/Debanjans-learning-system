Describe Azure identity, access, and security

Know identities, decisions, permissions, and layered protection.

Domain 2Azure architecture and services35–40%
In one minuteOfficial skillsDirectory and authConditional Access and RBACZero Trust and defense in depthEncryption and Key VaultDefender for CloudMCQsQuick recall

In one minute

  • Start with the identity presented; authentication answers who the principal is, while authorization answers what that identity may do.
  • Use SSO for one sign-in across trusted applications; use MFA for two or more factors; use passwordless when authentication must not require a password.
  • Use Conditional Access when sign-in context such as user, device, location, risk, or client type must drive a block or control; it is a per-sign-in decision.
  • Use RBAC when the scenario asks who may perform an Azure resource action; role definition, security principal, and scope determine the assignment.
  • Use Zero Trust to verify explicitly, use least privilege, and assume breach; use defense in depth when multiple independent protection layers are required.

Authentication (authn) answers “Who are you?” Authorization (authz) answers “What may you do?” Authentication comes first; authorization uses the authenticated identity, resource, action, and policy context to decide access.

Diagram: authentication proves identity; Conditional Access evaluates context; RBAC authorizes actions at scope.

  1. Identity is presented as the principal.

    The sign-in request presents an identity that will be evaluated.

  2. Authentication establishes identity using SSO, MFA, or passwordless.

    Authentication answers “Who are you?” and comes before authorization.

  3. Conditional Access evaluates sign-in signals and applies a decision.

    It evaluates user, group, application, device state, location, risk, and client type, then can block access or require controls such as MFA or a compliant device.

  4. RBAC authorizes permitted actions at scope.

    RBAC combines role definition, security principal, and scope to decide Azure resource actions.

Authentication methods

SSO
Sign in once, then access multiple trusted applications without a separate sign-in to each one.
MFA
Require two or more factors: something you know, something you have, or something you are. A password plus authenticator approval is stronger than password alone.
Passwordless
Authenticate without a password using methods such as Windows Hello, authenticator app, or FIDO2 security keys. Passwordless is not the same as MFA, though a passwordless method can use multiple factors.

External identities

External identities represent people outside your workforce tenant. B2B guest collaboration lets partner users access selected resources. Microsoft Entra External ID in an external tenant provides customer identity and access management (CIAM) for consumer and business-customer applications. Azure AD B2C is the legacy CIAM solution and is unavailable for new customers to purchase as of May 1, 2025. Multi-tenant applications can accept identities from multiple organizations/tenants when configured to do so.

ConfuseEntra ID is cloud identity and modern authentication. Entra Domain Services supplies managed legacy domain protocols and domain join. Neither distinction means “cloud vs on-prem only.”
Common wrong turn

“MFA and passwordless are the same requirement.” — MFA requires two or more factors; passwordless removes the password requirement, and a passwordless method can use multiple factors.

Memory hookAuthn = name the principal. Authz = name allowed action. MFA adds factors; passwordless removes password.

Conditional Access and RBAC

Microsoft Entra Conditional Access

Conditional Access, configured in the Microsoft Entra admin center, is Microsoft's Zero Trust policy engine. It evaluates signals → decision → enforcement for each sign-in or access attempt. Signals can include user, group, application, device state, location, risk, and client type. After first-factor authentication, it can block access or grant access subject to controls such as MFA or a compliant device. It is a per-sign-in policy decision, not a one-time identity label.

Azure role-based access control

Azure RBAC combines a role definition (management-plane Actions/NotActions and, for supported services, data-plane DataActions/NotDataActions), a security principal (user, group, service principal, or managed identity), and a scope (management group, subscription, resource group, or resource). Assignments can inherit down the hierarchy. Azure roles manage Azure resources; Microsoft Entra roles manage directory resources such as users, groups, and domains.

ScopeInheritance directionExample meaning
Management groupDown to subscriptions, resource groups, and resources.Grant a governance team read access across an estate.
SubscriptionDown to resource groups and resources.Grant an operations group access across one environment.
Resource groupDown to resources in that group.Let a team manage one application's resource collection.
ResourceDirect scope only.Grant narrow access to one storage account or VM.

RBAC is primarily allow-based: role assignments grant permitted actions at scope. Deny assignments are the exception and can block actions even where an allow exists. Least privilege means assign only required role and scope.

ConfuseRBAC grants resource actions. Conditional Access evaluates sign-in context and enforces access conditions. Azure Policy enforces resource configuration and standards; see file 09.
Common wrong turn

“Conditional Access grants Azure resource actions.” — Conditional Access evaluates sign-in context and access conditions; RBAC grants permitted resource actions at scope.

Exam clue“Who can delete this resource?” → RBAC. “Must this sign-in use MFA?” → Conditional Access. “Must resources have a tag or allowed location?” → Azure Policy.

Zero Trust and defense in depth

Zero Trust

Zero Trust replaces implicit trust with three habits: verify explicitly, use least privilege, and assume breach. Every request is evaluated using identity, device, context, and resource sensitivity; access is limited and monitored rather than trusted because a request came from an internal network.

Defense in depth

Defense in depth uses multiple independent protection layers. If one control fails, another layer can still reduce likelihood or impact. Azure revision order:

Diagram: defense in depth layers remain useful when one control fails.

Layers: physical → identity → perimeter → network → compute → application → data. The model is not one product; it is a design and review approach spanning facilities, accounts, traffic boundaries, hosts, software, and information.

ConfuseZero Trust is a security principle and decision model. Defense in depth is layered control design. They complement each other: verify every request while keeping multiple protective layers.
Common wrong turn

“Zero Trust is one product that replaces layered controls.” — Zero Trust is a security principle and decision model; defense in depth keeps multiple protective layers.

Encryption and key management

Encryption at rest protects stored data such as disks, databases, and storage accounts. Encryption in transit protects data while it moves between users, applications, and services.

Azure Key Vault centrally stores and controls secrets, encryption keys, and certificates. Use access control, rotation, auditing, and managed identities so applications retrieve secrets without hard-coded credentials.

ConfuseEncryption protects data confidentiality; RBAC and Key Vault access control govern who can use keys or secrets. At rest ≠ in transit.

Microsoft Defender for Cloud

Microsoft Defender for Cloud provides cloud security posture management and workload protection. It helps identify misconfiguration and risk, presents secure score/posture signals, recommends improvements, and can protect workloads across Azure, hybrid environments, and multicloud scenarios. Azure Arc can extend management and security visibility to supported resources outside Azure.

  • Posture management: find gaps, recommendations, compliance posture, and secure score signals.
  • Workload protection: threat protection for relevant servers, containers, databases, storage, and other workloads through applicable plans.
  • Hybrid coverage: connect supported non-Azure resources for management and security visibility, including through Azure Arc.
Exam clueDefender for Cloud is not the same as RBAC or Conditional Access. It assesses posture and helps protect workloads; RBAC controls resource actions; Conditional Access controls sign-in conditions.
Memory hookDefender for Cloud asks: “How secure is posture, and how are workloads protected?”

MCQs

  1. Which service is the cloud identity and directory service for modern authentication?
    • A. Microsoft Entra ID
    • B. Microsoft Entra Domain Services
    • C. Azure Files
    • D. Azure Policy
    Answer

    Answer: A — Microsoft Entra ID.

    Reason: Entra ID provides cloud identities, directory objects, modern authentication, SSO, and MFA.

    • B — Domain Services supplies managed legacy domain protocols and domain join.
    • C — Azure Files provides managed file shares.
    • D — Azure Policy governs resource configuration.
  2. A legacy application requires LDAP, Kerberos, NTLM, and domain join, but the team does not want to deploy domain controllers. Which service fits?
    • A. Microsoft Entra ID
    • B. Microsoft Entra Domain Services
    • C. Microsoft Defender for Cloud
    • D. Conditional Access
    Answer

    Answer: B — Microsoft Entra Domain Services.

    Reason: Domain Services provides managed compatibility with traditional domain protocols and join scenarios.

    • A — Entra ID focuses on cloud identity and modern protocols.
    • C — Defender for Cloud manages posture and workload protection.
    • D — Conditional Access evaluates sign-in context and controls access conditions.
  3. Which authentication method lets a user access multiple trusted applications after one sign-in?
    • A. SSO
    • B. RBAC
    • C. Defense in depth
    • D. Azure Resource Manager lock
    Answer

    Answer: A — SSO.

    Reason: Single sign-on reduces repeated application sign-ins after the identity is established.

    • B — RBAC authorizes Azure resource actions.
    • C — Defense in depth is layered protection design.
    • D — Resource locks are not an authentication method.
  4. A sign-in policy must require an authenticator approval when a user connects from a risky location. Which service makes this contextual decision?
    • A. Azure RBAC
    • B. Microsoft Entra Conditional Access
    • C. Microsoft Entra Domain Services
    • D. Azure Key Vault
    Answer

    Answer: B — Microsoft Entra Conditional Access.

    Reason: Conditional Access evaluates signals such as location and risk, then can require MFA or block access.

    • A — RBAC grants resource actions after identity and policy checks.
    • C — Domain Services supplies legacy domain compatibility.
    • D — Key Vault stores secrets, keys, and certificates.
  5. A team wants users to sign in without entering a password, using Windows Hello or a FIDO2 key. What is this?
    • A. Passwordless authentication
    • B. Azure RBAC
    • C. Region pairing
    • D. Defense in depth
    Answer

    Answer: A — Passwordless authentication.

    Reason: Passwordless methods authenticate without a password, including Windows Hello and FIDO2 keys.

    • B — RBAC is authorization for resource actions.
    • C — Region pairing is geographic resiliency support.
    • D — Defense in depth uses multiple security layers.
  6. An application team can read a storage account but must not delete it. Which control is primarily responsible for permitted Azure resource actions?
    • A. Conditional Access
    • B. Azure RBAC
    • C. SSO
    • D. Zero Trust alone
    Answer

    Answer: B — Azure RBAC.

    Reason: RBAC combines role definition, principal, and scope to grant resource actions.

    • A — Conditional Access governs sign-in conditions, not the role's action list.
    • C — SSO reduces repeated sign-ins.
    • D — Zero Trust guides decisions but does not itself assign Azure actions.
  7. Which statement correctly distinguishes MFA from passwordless authentication?
    • A. MFA requires two or more factors; passwordless removes the password requirement
    • B. MFA is authorization; passwordless is a network route
    • C. MFA only uses passwords; passwordless always uses two passwords
    • D. They are names for RBAC scopes
    Answer

    Answer: A — MFA requires two or more factors; passwordless removes the password requirement.

    Reason: They describe different properties and can overlap in one authentication method.

    • B — MFA and passwordless are authentication concepts.
    • C — MFA does not require passwords, and passwordless uses no password.
    • D — RBAC scopes concern authorization targets.
  8. A policy says a device must be compliant before sign-in proceeds. Is this primarily RBAC or Conditional Access?
    • A. RBAC
    • B. Conditional Access
    • C. Azure Key Vault
    • D. Entra Domain Services
    Answer

    Answer: B — Conditional Access.

    Reason: Device state is a sign-in signal used by Conditional Access to enforce a decision.

    • A — RBAC decides allowed resource actions after access is granted.
    • C — Key Vault manages secrets and keys.
    • D — Domain Services supports legacy domain protocols.
  9. Which statement best describes Zero Trust?
    • A. Trust every request from an internal network
    • B. Verify explicitly, use least privilege, and assume breach
    • C. Use one firewall as the only control
    • D. Put all resources in one subnet
    Answer

    Answer: B — Verify explicitly, use least privilege, and assume breach.

    Reason: Zero Trust is a principle and decision model that rejects implicit trust.

    • A — Zero Trust does not trust based only on network location.
    • C — One control contradicts layered protection.
    • D — Network layout alone is not Zero Trust.
  10. Which statement best distinguishes defense in depth from Zero Trust?
    • A. Defense in depth uses multiple protection layers; Zero Trust evaluates every request
    • B. Defense in depth is only password policy; Zero Trust is only physical security
    • C. They are identical names for Conditional Access
    • D. Defense in depth replaces RBAC authorization
    Answer

    Answer: A — Defense in depth uses multiple protection layers; Zero Trust evaluates every request.

    Reason: Layered controls and explicit verification complement each other but are distinct concepts.

    • B — Both concepts span multiple security concerns.
    • C — Neither is merely another name for Conditional Access.
    • D — RBAC remains an authorization control.
