Diagnostics and repository automation

Use observable evidence to debug a run, then verify automation output before trusting it.

Domain 3Claude Code configuration and workflowsWeight unverified
In one minuteSkills in scopeStatus and debugRun evidenceRepository automationValidate changeMCQsQuick recall

In one minute

  • Start diagnosis with observed provider, authentication, tool state, and reproduction evidence; a remembered command or label is not current product proof.
  • Record formatted output, logs, and persisted artifacts; a UI view or completion message alone is not durable completion evidence.
  • Keep secrets and diagnostic material scoped and reviewed before sharing; debug detail can expose more than the visible symptom.
  • Automate only after defining trigger, authority, secret handling, branch or PR outcome, and review path; a workflow trigger does not prove a correct repository change.
  • Validate generated, refactored, or ported work in its target environment; successful syntax or a friendly response is not behavioral verification.

Skills in scope

This provisional mapping remains subject to the official guide when it is published.

  • Use status and debug evidence to diagnose provider, authentication, tool state, and reproducible faults.
  • Treat logs, formatted output, and persisted artifacts as evidence distinct from UI or completion wording.
  • Evaluate workflow triggers, permissions, secrets, branches, PRs, and latency before automation trust.
  • Validate generated, refactored, or ported implementation against behavior, artifacts, and target SDK.

Status and debug evidence

A status surface can expose the active provider, authentication state, and available tool state for a running environment. A debug log can capture fuller diagnostic detail when an issue is reproduced. Exact diagnostic commands, fields, log paths, and output wording are version-sensitive; inspect the current product documentation and the actual run rather than memorizing a command-line sequence.

Use an evidence-first investigation when a task does not behave as expected. First state the symptom and expected behavior. Then record status output, the relevant input, tool state, and a reproduction. Finally inspect generated diagnostic output and the changed artifact. This separates a provider or authentication mismatch from a tool-state issue, a malformed input, or a stale display.

  1. Define a repeatable symptom and the expected result.

    Make the failing behavior specific enough to rerun. A vague report such as “it did not work” does not identify a testable boundary.

  2. Capture current status and relevant debug evidence.

    Record the observed provider, authentication indication, enabled tool state, and diagnostic output without assuming any version-specific label is stable.

  3. Reproduce with controlled input and inspect the resulting artifacts.

    Compare logs, returned output, file changes, and other persisted results with the intended behavior.

  4. Constrain the next change to the evidence found.

    Fix or escalate the identified boundary, then rerun the same check instead of treating a changed UI message as proof.

Common wrong turn

“Installed means authenticated and ready.” — Installation, an active authenticated session, selected provider, tool state, and a successful smoke test are separate observations. Check the target environment rather than inferring one from another.

Reported completion versus durable evidence

Readable terminal output helps a person interpret a run, but it is not the same thing as a persisted result. Format raw output for inspection, retain relevant logs, and check the expected artifact directly. An finding or changed file can be evidence when it exists, is readable, and matches the intended work; a visible completion phrase only reports what a layer chose to say.

Keep a provenance trail where a later reviewer needs to connect a claim, action, or result to the run that produced it. For a code change, that might mean the relevant changed files, validation output, and reviewable branch or PR state. Do not expose credentials, private logs, or unrelated files merely to make a report look complete.

ConfuseCompletion text is reported success. Durable completion is verified artifact evidence. Complete wording can appear without a durable file, branch, PR, or report; inspect the artifact before declaring work complete.

Worked scenario: repository automation

A repository workflow may begin after a configured event, start an isolated runner, invoke an action, and produce a branch or PR for inspection. Treat the whole path as a proposed automation, not a trusted result. Exact workflow YAML keys, action names, runner behavior, trigger syntax, and authentication setup are UNVERIFIED version-sensitive details; validate them in the target repository without placing a secret in source.

Diagram text equivalent: a configured trigger reaches a runner, the runner executes an action, and the resulting branch or PR is inspected. This is a review path, not a claim that every trigger automatically creates a correct PR.

Before trusting this path, define the event that should start it, the repository authority required, how a secret is supplied outside source, the expected branch or PR behavior, and who reviews the change. Account for runner startup and asynchronous feedback: automation can be useful when immediate conversation is not required, but latency and delayed review are real operational constraints.

Common wrong turn

“A workflow run completed, so the repository change is ready to merge.” — Completion can precede a missing branch association, an empty or wrong diff, a merge conflict, failed validation, or a review failure. Inspect the durable repository outputs before merge.

Validate the change at its boundary

Generated code, a refactor, and an SDK port can look plausible while changing behavior. Select a validation method from the risk: inspect the diff for scope, run a focused behavior check, verify required artifacts, and test the target SDK or environment where version-sensitive behavior matters. A target SDK claim needs evidence from that target language and version, not a copied snippet from a different binding.

Change or claimValidation evidenceInsufficient shortcut
Generated implementationFocused behavior check, expected output, and inspectable changed artifact.Generated code parses or the agent says it completed.
RefactorPreserved behavior plus readable ownership boundaries and updated artifacts.Files moved without rerunning the affected workflow.

Constraint to choice: if the result must affect a repository, choose a reviewable branch or PR plus targeted validation; if a claim depends on a product surface, choose target-version documentation and an observed smoke test; if evidence is missing, keep the conclusion provisional rather than increasing automation authority.

Common wrong turn

“A successful port proves feature equivalence.” — One run only supports the observed scenario. Check supported fields, tool boundaries, error behavior, and artifacts in the actual target SDK before claiming equivalent behavior.

MCQs

  1. A coding environment reports an unexpected provider and tool state. What is the strongest first diagnostic move?
    • A. Assume a remembered status label means the intended environment is active
    • B. Capture current status, relevant tool state, and a reproducible symptom
    • C. Change authentication settings until the visible message looks familiar
    • D. Skip diagnostic evidence and rerun the task repeatedly
    Answer

    Answer: B — Capture current status, relevant tool state, and a reproducible symptom.

    Reason: Current observed state and a controlled reproduction distinguish provider, authentication, tool, and input boundaries without relying on version-sensitive wording.

    • A — Remembered labels are useful when comparing a documented known environment, but they are not evidence that this target state is active.
    • C — Changing authentication is appropriate after evidence identifies an authentication mismatch, not before status and symptom evidence establish the cause.
    • D — Repeating a run is appropriate after defining a controlled reproduction, not as a substitute for diagnostic evidence.
  2. A run displays “completed” but the expected report file is absent. What should the team conclude?
    • A. The completion message proves the report was written
    • B. The UI is the durable source of truth
    • C. The run is incomplete until the expected persisted artifact is inspected
    • D. A formatted terminal message replaces a missing file
    Answer

    Answer: C — The run is incomplete until the expected persisted artifact is inspected.

    Reason: Reported completion and durable completion differ; absence of the expected artifact prevents verification of the claimed result.

    • A — A completion message is useful when reporting a layer status, but it does not establish a file write or artifact content.
    • B — A UI is useful for presentation and quick feedback, not as the only durable evidence of repository or file state.
    • D — Formatted output is useful for human inspection, but it cannot replace the artifact required by the workflow.
  3. A team needs to share diagnostic output with another reviewer. Which practice best fits evidence discipline?
    • A. Send every log and credential so the reviewer has complete access
    • B. Review, minimize, and redact diagnostic material while retaining the evidence needed to reproduce
    • C. Send only a screenshot of the completion message
    • D. Delete all logs before checking whether the reviewer can reproduce the issue
    Answer

    Answer: B — Review, minimize, and redact diagnostic material while retaining the evidence needed to reproduce.

    Reason: Logs can support reproduction but may include sensitive or unrelated material, so evidence sharing needs scope and review.

    • A — Broad disclosure is appropriate only under an explicitly authorized secure incident process, not as a default diagnostic practice.
    • C — A screenshot is appropriate for showing a visible symptom, but it usually lacks the structured evidence needed for reproduction.
    • D — Deletion is appropriate under a retention or privacy policy after evidence handling is complete, not before diagnosis can be reproduced.
  4. A repository workflow should propose a change after a configured event. What must be verified before the team trusts the automation?
    • A. Only that the event can start a runner
    • B. Trigger, authority, secret handling, branch or PR outcome, validation, and review path
    • C. Only that a response mentions a pull request
    • D. That the workflow uses a remembered YAML key and action name
    Answer

    Answer: B — Trigger, authority, secret handling, branch or PR outcome, validation, and review path.

    Reason: A repository automation path is trustworthy only after its event, permissions, protected secret path, durable output, and reviewable behavior are verified.

    • A — Runner startup is relevant when assessing latency and execution, but it does not verify authority, outputs, or review controls.
    • C — A PR message is useful when it links to an inspected review artifact, but wording alone does not prove the right branch or diff exists.
    • D — Exact configuration syntax is appropriate to verify against current documentation, but remembered version-sensitive names are not the whole automation validation.
  5. A refactor moves code into clearer modules. What evidence best supports the claim that it is safe?
    • A. The new file layout looks more organized
    • B. The generator says the refactor preserved behavior
    • C. The affected workflow still behaves as expected and its required artifacts can be inspected
    • D. The old files were deleted without an error message
    Answer

    Answer: C — The affected workflow still behaves as expected and its required artifacts can be inspected.

    Reason: Refactoring needs behavior-preservation evidence, not only a structural or conversational claim.

    • A — Clear ownership boundaries are useful for maintainability, but organization alone does not verify preserved behavior.
    • B — A generator report is useful as a hypothesis about what changed, not as validation of runtime behavior.
    • D — Deleting obsolete files is appropriate after migration is confirmed, but lack of an error message does not prove the workflow remains correct.
  6. A port works once in a target application, but documentation from another language describes extra controls. What is the defensible next step?
    • A. Claim feature equivalence because the smoke test passed
    • B. Copy the other language fields into the target configuration
    • C. Validate target-language and target-version support, then test the relevant behavior and artifacts
    • D. Treat the other language documentation as the target SDK contract
    Answer

    Answer: C — Validate target-language and target-version support, then test the relevant behavior and artifacts.

    Reason: A smoke test supports one observed path; cross-SDK field and behavior claims remain version-specific until validated in the actual target.

    • A — Feature equivalence is appropriate only after the relevant target behaviors and boundaries have been tested, not after one successful path.
    • B — Copying fields is appropriate only when target documentation and a test confirm they are supported and correctly configured.
    • D — Another language guide is useful as a comparison hypothesis, not as authoritative proof of target SDK capability.

Quick recall

Attempt each question before expanding it.

What evidence should a reproducible diagnostic record capture before you change configuration?

State the specific symptom and expected result, then capture current provider, authentication indication, relevant tool state, controlled input, and diagnostic output. Exact command names and fields require current-product verification.

Why is a completion message insufficient evidence that a run completed?

It reports a status from one layer. Verify the expected persisted artifact, such as a file, report, branch, PR, or other output, then inspect its content and related validation evidence.

How should diagnostic logs be prepared for sharing?

Retain the minimum evidence needed for reproduction, correlate it to the run, and review or redact secrets, private data, and unrelated material before sharing through an approved path.

What repository automation boundaries should be verified before trust?

Verify the event trigger, required authority, secret handling outside source, runner and latency behavior, action result, branch or PR association, focused validation, and human review path.

What proves a refactor preserved behavior more strongly than a clean file layout?

Run the affected behavior check, inspect expected outputs and changed artifacts, and compare them with the intended result. Readability helps maintenance but does not alone prove preservation.

Why does a target SDK port need its own validation even after another SDK example works?

Language bindings, versions, fields, dependencies, tool boundaries, and error behavior can differ. Validate the actual target documentation and run the relevant target behavior and artifact checks.
