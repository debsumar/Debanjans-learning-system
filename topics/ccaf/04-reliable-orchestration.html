Reliable orchestration and recovery

Turn partial multi-agent work into bounded, inspectable, and resumable progress.

Domain 1Agentic architecture and orchestrationWeight unverified
In one minuteSkills in scopeBounded refinementStructured reportsAudit evidenceRecovery scenarioMCQsQuick recall

In one minute

  • Evaluate coverage after initial work; do not finalize before an explicit evaluation gate permits it.
  • Refine identified gaps only; do not rerun every completed partition merely because coverage is incomplete.
  • Bound refinement iterations; an iteration bound limits repeated coverage work but does not prove output quality or accuracy.
  • Return success, empty, partial, and failure context in a structured report; a generic error cannot support synthesis.
  • Record scoped calls, inputs, outputs, errors, latency, IDs, and coverage evidence; console text alone is not an audit trail.
  • Treat recovery as operational only when automatic coordination runs before every dispatch; validation retry corrects an artifact, not an interrupted task.

Skills in scope

This provisional mapping remains subject to the official guide when it is published.

  • Implement coverage evaluation, gap-only refinement, bounded attempts, and finalization gates.
  • Preserve structured sub-agent success, empty-result, partial-result, and failure context.
  • Design auditability with scoped calls, inputs/outputs, errors, latency, IDs, and coverage evidence.
  • Reconcile interrupted task state and resume durable work beyond a happy-path smoke test.

Bounded refinement

A refinement loop feeds coverage evaluation back into work. Initial partitions finish first; the coordinator evaluates what remains, delegates only identified gaps when coverage is insufficient, and finalizes only through a gate. The transcript example uses a configured iteration bound, but does not establish a universal threshold or a validation-remediation policy.

  1. Collect initial partition reports before judging coverage.

    Evaluation needs the completed initial work and its evidence, not a final-looking response alone.

  2. Evaluate coverage and identify a specific missing dimension.

    A coverage signal selects what still needs work; score movement by itself does not establish quality.

  3. Delegate only the identified gap while refinement iterations remain.

    Keep prior completed work and add targeted evidence rather than repeat the entire pipeline.

  4. Pass the finalization gate or stop at the configured iteration bound.

    Final output follows a permitted evaluation result; exhaustion of the bound is a control outcome, not proof that the result is sufficient.

Flow: initial work reaches a coverage check; sufficient coverage reaches the terminal gate, while an identified gap receives bounded iteration work before another check. This is the text equivalent of the diagram.

Structural prerequisite enforcement

An evaluation or finalization gate decides whether collected work is sufficient to proceed. A prerequisite gate is different: it blocks an action whose required prior condition is absent. Prompt guidance can state “research before synthesis,” but guidance alone can be ignored.

Enforce the order structurally: block synthesis in a pre-tool check until required research exists, inspect the tool result in a post-tool check, and permit synthesis only after the required research result passes that inspection. Pre-tool blocking and post-tool inspection enforce prerequisites; evaluation and finalization gates judge coverage and release the final result.

Common wrong turn

“Refinement means rerun every agent until the result looks good.” — The planned control evaluates coverage, targets identified gaps, bounds refinement iterations, and keeps finalization behind an explicit gate.

Structured reports preserve outcome context

A structured report lets a coordinator distinguish usable evidence from a valid empty result, partial result, or failure. This avoids both silent suppression and ending all work solely because one specialist had a problem.

OutcomeContext to preserveCoordinator treatment
SuccessStatus, sub-agent identity, summary, evidence, and attempts.Use the result in coverage evaluation and synthesis.
Valid empty resultStatus, scope, and evidence that the domain finding is empty or insufficient.Keep it visible; do not disguise it as a tool or access failure.
Partial resultCompleted evidence, remaining limitation, attempted approaches, and coverage effect.Synthesize available work and decide whether an identified gap needs follow-up.
FailureTyped failure, attempted approaches, errors, and any partial context.Record it for recovery or a bounded local response instead of silently dropping it.

Scope specialist tools to their assigned domain. A broad tool set can make a specialist appear flexible, but it weakens the boundary needed to understand which call produced which evidence.

Audit evidence at the coordinator boundary

Observability is evidence about execution, not a final message. For each scoped call, retain its partition or question association, input, output or error, identifier, latency, and coverage result. Persisted records and structured traces support later inspection when a synthesis cannot explain its recommendation.

A partition described only in coordinator data is advisory if a spoke can still answer outside it. Enforce scope at the spoke boundary and retain evidence when out-of-scope work is rejected or recorded. A final recommendation should follow an explicit coverage gate, not merely a logged score or a successful-looking console print.

Test the boundary in stages: first send a clearly out-of-scope request and verify rejection or recording; then add irrelevant or conflicting context to a valid request and verify that the spoke preserves its assigned scope. Retain both test traces. A stated scope is not evidence that the boundary resists context pollution.

Common wrong turn

“Console output is an audit trail.” — Print-only output is ephemeral. Auditability needs durable, scoped execution evidence such as inputs, outputs, errors, IDs, latency, and coverage state.

Worked scenario: resume durable exploration

Recovery is operational only when a coordinator boundary runs automatically before every dispatch. The demonstrated coordinator was invoked manually, so a manually runnable startup scan is a gap, not proof of recovery. At that automatic pre-dispatch boundary, scan recorded task state, reconcile stuck work, then resume only work still required.

Persist task state and append findings incrementally during exploration. Reconciliation can resume recorded work, but it cannot restore a finding or state transition that was never written: only state committed before the failure is recoverable.

Failure-injection path

  1. Append each durable finding and update task state as work progresses.

    Do not wait until the end of a long exploration to write the scratchpad or manifest.

  2. Inject a parent interruption after an incremental write.

    Confirm that the committed finding remains and that any unwritten work is absent rather than invented during reconciliation.

  3. Run automatic pre-dispatch reconciliation, then resume required work.

    Inspect the reconciled task, appended finding, and resumed dispatch rather than treating a completion message as durable evidence.

  4. Synthesize from scratchpads through one result path.

    Use scratchpads plus synthesis as the result path; do not maintain a competing results JSON that duplicates or conflicts with that state.

Validation retry corrects an artifact by returning specific errors and attempting a revised result within a defined remediation bound. Task recovery resumes an interrupted durable task after automatic pre-dispatch reconciliation. They can both be bounded, but retry changes a result while recovery restores only progress that was durably recorded.

ConfuseRetry corrects an artifact after validation feedback; recovery resumes an interrupted durable task from reconciled state. A retry may produce a new result, while recovery preserves task context and continues durable work.

Test the non-happy path deliberately: append state, inject an interruption, allow the automatic pre-dispatch boundary to reconcile recorded work, resume what remains, and inspect the scratchpad and synthesis path. A completion message alone does not prove the durable artifact or recovery path succeeded.

MCQs

  1. Initial research reports omit evidence for one required dimension. What should a bounded refinement coordinator do next?
    • A. Rerun every completed partition
    • B. Finalize because initial calls completed
    • C. Delegate only the identified gap if the iteration bound allows another refinement pass
    • D. Increase attempts until output looks detailed
    Answer

    Answer: C — Delegate only the identified gap if the iteration bound allows another refinement pass.

    Reason: Gap-only refinement uses coverage evidence to target missing work within a configured iteration bound.

    • A — Rerunning every partition is correct when all prior results are invalidated, not when one identified gap remains.
    • B — Finalizing is correct when the evaluation gate permits sufficient coverage, not merely when initial calls completed.
    • D — Increasing attempts is correct only after a separately justified configuration decision, not as a substitute for gap evaluation.
  2. A coverage indicator rises after another pass. What conclusion is supported?
    • A. The output is proven accurate
    • B. The indicator can guide the next coverage decision
    • C. Every source is now diverse
    • D. The iteration bound is unnecessary
    Answer

    Answer: B — The indicator can guide the next coverage decision.

    Reason: A coverage signal can guide control flow, but observed movement alone does not validate quality or accuracy.

    • A — Proof of accuracy is correct only after suitable empirical evaluation, not from score movement alone.
    • C — Source diversity is correct when source evidence has been separately inspected, not from one coverage indicator.
    • D — Removing an iteration bound is correct only for a workflow with another reliable runaway control, not because one pass improved a signal.
  3. A notification specialist lacks permission but has already gathered useful context. Which report best supports synthesis?
    • A. A generic error string only
    • B. No report, so the workflow can continue quietly
    • C. Status, specialist identity, attempted approaches, typed failure, and partial context
    • D. A success status because some context exists
    Answer

    Answer: C — Status, specialist identity, attempted approaches, typed failure, and partial context.

    Reason: Structured context lets the coordinator distinguish a failure from usable partial evidence and select a response.

    • A — A generic error is correct only for a user-facing minimal notification, not for coordinator synthesis and recovery.
    • B — Omitting a report is correct only when no task was dispatched, not after a specialist encountered an outcome.
    • D — Success is correct when the assigned action completed as required, not when permission blocked it.
  4. An inventory specialist returns zero matching items from a valid query. How should the coordinator classify it?
    • A. Valid empty result with its scope and evidence
    • B. Access failure
    • C. Silent success with no record
    • D. Partial result caused by an iteration bound
    Answer

    Answer: A — Valid empty result with its scope and evidence.

    Reason: Zero matching items can be a legitimate domain finding, unlike inability to perform an action.

    • B — Access failure is correct when authorization or connectivity prevents the assigned action, not when a valid query finds none.
    • C — Silent success is correct only for a non-audited disposable action, not for evidence needed by a coordinator.
    • D — Partial result is correct when some requested work remains incomplete, not when a valid query has a complete empty finding.
  5. A recommendation cannot be explained after a run. Which record set most directly improves auditability?
    • A. Final answer text and a screenshot
    • B. Scoped calls with inputs, outputs or errors, latency, IDs, and coverage evidence
    • C. A larger prompt containing every prior message
    • D. A list of specialist names only
    Answer

    Answer: B — Scoped calls with inputs, outputs or errors, latency, IDs, and coverage evidence.

    Reason: These records connect execution, control state, and evidence to a particular recommendation.

    • A — Final text and a screenshot are correct when presenting a result, not when reconstructing its execution path.
    • C — Full history is correct when a human must review conversation context, not as a focused durable audit record.
    • D — Specialist names are correct when building a roster, not when identifying inputs, outputs, failures, or timing.
  6. A partition scope exists in coordinator JSON, but the specialist can answer any unrelated question. What control is missing?
    • A. A longer final summary
    • B. Spoke-level scope enforcement
    • C. An additional synthesis agent
    • D. A higher coverage score
    Answer

    Answer: B — Spoke-level scope enforcement.

    Reason: A coordinator-side description is advisory until the receiving specialist validates or rejects out-of-scope work.

    • A — A longer summary is correct when reader-facing explanation lacks detail, not when execution boundaries are unenforced.
    • C — Another synthesizer is correct when independent aggregation is needed, not when a specialist accepts unrelated scope.
    • D — A higher score is correct only if an evaluation method justifies it, not as enforcement of an assigned boundary.
  7. A parent process stops while task state remains recorded as running. Which control makes reconciliation operational recovery?
    • A. Treat running state as completed
    • B. Delete all prior findings
    • C. Automatically invoke pre-dispatch reconciliation, then resume required durable work
    • D. Blindly repeat validation of the last artifact
    Answer

    Answer: C — Automatically invoke pre-dispatch reconciliation, then resume required durable work.

    Reason: Recovery begins only when every dispatch path invokes reconciliation of recorded state and preserved artifacts; a manually runnable coordinator is not operational recovery.

    • A — Treating state as completed is correct only after durable completion evidence is verified, not because a row says running.
    • B — Deleting findings is correct only for an intentional invalidation policy, not as normal interruption recovery.
    • D — Artifact validation retry is correct when a correctable output defect is under review, not for interrupted task-state reconciliation.
  8. A team tested only normal completion. Which next test best evaluates recovery?
    • A. Inject an interruption and inspect reconciliation and resumed findings
    • B. Make the final response friendlier
    • C. Run more successful smoke tests
    • D. Remove persisted task state
    Answer

    Answer: A — Inject an interruption and inspect reconciliation and resumed findings.

    Reason: A deliberate failure test exercises the path a happy-path smoke test does not cover.

    • B — Friendlier text is correct when user presentation needs improvement, not when interruption handling is untested.
    • C — More smoke tests are correct when increasing confidence in normal behavior, not when evidence of recovery behavior is required.
    • D — Removing state is correct only for intentional cleanup after verified completion, not for testing resume capability.
  9. A validator returns a specific format error for an artifact, while a prior task was interrupted after partial progress. Which pairing is correct?
    • A. Resume the artifact and retry the interrupted task
    • B. Retry the artifact with error feedback and recover the task from reconciled state
    • C. Finalize both because each has some output
    • D. Discard both histories and restart all work
    Answer

    Answer: B — Retry the artifact with error feedback and recover the task from reconciled state.

    Reason: Retry corrects a validation defect; recovery resumes durable interrupted work while preserving its context.

    • A — Resuming is correct when task state was interrupted and retrying is correct when an artifact is correctable, but this option reverses those roles.
    • C — Finalizing is correct only after evaluation and durable-completion gates permit it, not because partial output exists.
    • D — Restarting all work is correct only when state and artifacts are unusable, not as the default for a specific validation error and recoverable task.

Quick recall

Attempt each question before expanding it.

What sequence makes refinement bounded rather than a whole-pipeline rerun?

Collect initial reports, evaluate coverage, identify a gap, delegate only that gap while the iteration bound allows another refinement pass, then pass a finalization gate or stop at that bound.

Why does a coverage score not prove output quality?

It can guide a control decision, but observed score movement needs representative evaluation and testing before it supports a quality or accuracy claim.

Name the outcome contexts a structured sub-agent report must distinguish.

Success, valid empty result, partial result, and failure, with status, identity, summary or evidence, attempts, and relevant error or limitation context.

Why is a valid empty result not the same as an access failure?

An empty result can be a complete domain finding from a valid query. An access failure means the specialist could not perform the permitted action and needs typed failure context.

Which execution facts make a coordinator call auditable?

Retain scoped call or partition association, inputs, outputs or errors, latency, identifiers, and coverage evidence in durable records or structured traces.

Why is coordinator-only partition scope insufficient?

It is advisory if the specialist can answer outside it. The spoke needs its own scope enforcement, with out-of-scope work rejected or recorded.

What makes reconciliation operational after an interrupted task?

Every dispatch path automatically invokes the coordinator boundary first; it scans recorded task state, identifies or marks stuck running or failed work, preserves durable context already written, and resumes work that remains required.

Contrast validation retry with task recovery.

Validation retry returns specific artifact errors and reattempts correction within a defined remediation bound. Task recovery reconciles interrupted durable state and resumes preserved work; it is not merely another output correction.

What evidence should you inspect before trusting a recovery claim?

Inspect reconciled task state, resumed or appended findings, structured specialist reports and errors, scoped call records, and durable artifacts rather than completion wording alone.
