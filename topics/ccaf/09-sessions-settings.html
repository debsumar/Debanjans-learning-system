Sessions, context, and settings

Choose session state deliberately, preserve only needed continuity, and place configuration at its proper scope.

Domain 3Claude Code configuration and workflowsWeight unverified
In one minuteSkills in scopeSession lifecycleContext decisionsSettings scopesVersion checksMCQsQuick recall

In one minute

  • Resume when one continuing conversation needs its prior state; fork when an independent branch must preserve the original.
  • Rewind changes the current conversation point; inspect loss risk before it can remove later material.
  • Inspect active-session context before acting; compact for summarized continuity, clear only for a fresh conversation state.
  • Use managed scope for organization control, user for personal cross-project defaults, project for shared repository conventions, and local for untracked project-specific preference.
  • Commands, file names, retention, precedence details, and SDK capabilities are version-sensitive; verify target behavior instead of treating transcript examples as current contracts.

Skills in scope

This provisional mapping remains subject to the official guide when it is published.

  • Distinguish new, resumed, forked, rewound, compacted, and cleared session states.
  • Inspect active-session context and decide whether continuity, compaction, or clearing fits.
  • Select managed, user, project, or local settings by scope, Git treatment, and precedence.
  • Verify SDK/session commands, retention, and version-specific capabilities empirically.

Session lifecycle choices

A session is a conversation with accumulated state. Start a new conversation when prior history is not needed. Fork-based session management creates a managed branch with its own identity and recorded history from a shared baseline; that branch can later resume by its identity. Merely copying baseline messages creates a prompt copy, not a managed fork with separate identity or resumable history. Resume continues a chosen prior conversation, while rewind changes the current conversation back toward an earlier point.

Diagram: begin from a baseline. Resume continues it, fork creates an isolated branch, rewind changes its selected point, then a context decision can preserve summarized continuity or remove conversation history.

  • Sibling managed forks remain isolated after the baseline. Resume preserves the selected branch history; it does not merge later sibling results.
Common wrong turn

“A fork is a renamed resume.” — Resume continues one existing conversation. A fork preserves the source conversation while creating a distinct branch for divergence.

Decide from active-session context

Context window inspection concerns the active conversation, not an account-wide measure. Read category use and available headroom after switching or resuming a session. Autocompaction reserves headroom so conversation history can be summarized as limits approach; available capacity is therefore not all ordinary working room. The exact command, thresholds, automatic behavior, and category names are version-sensitive, so use current product evidence rather than an assumed fixed threshold.

Decision rule: choose compact when a shorter summary can retain continuity. Choose clear only when the next work should start without conversation history. Clear removes conversation history, but non-conversation guidance or memory can persist; it does not necessarily reset every source of instruction. Neither choice is a claim about a particular current command string or retained artifact behavior.

ConfuseCompact reduces context by retaining summarized continuity. Clear removes current conversation history for a fresh state. Compact and clear are not interchangeable, and clear is not merely terminal-screen clearing.
  1. Inspect the currently active session before a long continuation.

    Read current context use and headroom after resume or session switching; another session can have different state.

  2. Choose whether prior conversation must remain useful.

    If it must remain useful in shorter form, compact may fit. If it must not influence the next task, clear may fit.

  3. Confirm the effect in the target version before relying on it.

    Check current documentation or a safe controlled observation for command semantics, persistence, and recovery behavior.

Common wrong turn

“Autocompaction means context never needs inspection.” — Automatic behavior and thresholds can change. Inspect the active session when continuity or available room matters.

Place settings by audience and Git treatment

Settings precedence resolves conflict between scopes, while scope answers who should own a setting. The transcript describes managed, user, project, and local scopes: when settings conflict, higher scope wins. Exact setting names, locations, legal scopes, and implementation details remain version-sensitive.

For a conflict, identify the intended owner first, then apply the source rule: higher scope wins. Verify the current hierarchy and whether the setting is permitted in that scope. Do not infer precedence from where a setting happens to live.

Common wrong turn

“Repository-specific always means committed.” — Local preference can be project-specific while remaining untracked. Select project scope only when collaborators should receive the convention.

Verify volatile operational claims

Transcript demonstrations support distinctions and test design, not timeless product contracts. Treat session commands, flags, file locations, retention periods, storage behavior, SDK language parity, setting names, and precedence details as UNVERIFIED until checked against the target version.

Verify before relyingTest a minimal new, resume, fork, compact, clear, and rewind scenario in a safe workspace. Observe identifiers, state isolation, workspace effects, and resulting artifacts. Record what evidence supports, then stop short of claiming undocumented retention or recovery guarantees.

General author safety practice: use reversible tests on non-sensitive data when practical. This safety guidance is not a transcript procedure.

MCQs

  1. A developer must continue a prior investigation with its earlier reasoning. Which state choice fits?
    • A. New session
    • B. Resume
    • C. Fork
    • D. Clear
    Answer

    Answer: B — Resume.

    Reason: Resume is the continuation choice when one prior conversation's state is needed.

    • A — A new session fits when no earlier conversation is needed, unlike this continuation task.
    • C — Fork fits an independent divergent follow-up while preserving an original, not ordinary continuation.
    • D — Clear fits a fresh conversation state, opposite to preserving earlier reasoning.
  2. One completed analysis must support two independent follow-up hypotheses without changing the source conversation. Which choice fits?
    • A. Resume the source for both hypotheses
    • B. Fork separate branches from the baseline
    • C. Clear the baseline before each hypothesis
    • D. Rewind the baseline after each question
    Answer

    Answer: B — Fork separate branches from the baseline.

    Reason: Fork preserves shared prior history while isolating later branch state.

    • A — Resume fits one continuing conversation, but later work would accumulate in the same source state.
    • C — Clear fits discarding conversation history, not preserving a common analysis baseline.
    • D — Rewind fits moving a current conversation point, not creating independent preserved branches.
  3. A later conversation segment may be lost if an earlier point is selected. Which operation needs loss-risk review?
    • A. Rewind
    • B. Resume
    • C. Rename
    • D. New session
    Answer

    Answer: A — Rewind.

    Reason: Rewind changes the current conversation toward an earlier point, so later history requires deliberate loss review.

    • B — Resume fits continuing prior state, not intentionally moving its history point backward.
    • C — Rename fits human identification of a session, not changing conversation history.
    • D — A new session fits work without prior state, not altering an existing history.
  4. A team needs a stable label so several related conversations can be selected later. What is the direct organizational action?
    • A. Rename the session
    • B. Compact the session
    • C. Clear the session
    • D. Change settings scope
    Answer

    Answer: A — Rename the session.

    Reason: Rename improves human session identification without claiming a change to the underlying conversation state.

    • B — Compact fits reducing context while retaining a summary, not labeling related conversations.
    • C — Clear fits starting without conversation history, not making a session easier to recognize.
    • D — Settings scope fits configuration ownership, not an individual session label.
  5. Before a long continuation after switching sessions, what should the operator inspect?
    • A. Account-wide usage only
    • B. Active-session context use and headroom
    • C. A sibling branch's messages
    • D. A guessed retention period
    Answer

    Answer: B — Active-session context use and headroom.

    Reason: Context inspection concerns the currently active conversation and informs its continuity decision.

    • A — Account usage fits billing or subscription review, not direct inspection of this conversation window.
    • C — Sibling messages fit examining a separate branch, not measuring the active session's context.
    • D — Retention fits version-sensitive storage policy review, not present context capacity.
  6. A task needs less context but still needs a short representation of prior decisions. What fits?
    • A. Clear
    • B. Compact
    • C. New session
    • D. Fork
    Answer

    Answer: B — Compact.

    Reason: Compaction is the summarized-continuity choice when reducing context use.

    • A — Clear fits removing current conversation history, not retaining a summary for continuity.
    • C — A new session fits no needed prior history, which conflicts with this requirement.
    • D — Fork fits an independent branch from history, not primarily context reduction.
  7. A task is unrelated and prior conversation must not influence it. Which choice fits?
    • A. Resume
    • B. Compact
    • C. Clear
    • D. Rewind
    Answer

    Answer: C — Clear.

    Reason: Clear is the fresh-conversation choice when current history should not remain in the task context.

    • A — Resume fits carrying forward prior conversation state, opposite to this requirement.
    • B — Compact fits retaining summarized continuity, still contrary to no prior influence.
    • D — Rewind fits selecting an earlier history point, not removing the need for prior conversation state.
  8. A company must enforce one configuration rule for everyone. Which scope fits the ownership need?
    • A. Local
    • B. Project
    • C. User
    • D. Managed
    Answer

    Answer: D — Managed.

    Reason: Managed scope represents organization-controlled policy in the transcript framing.

    • A — Local fits one user's project-specific untracked preference, not organization-wide enforcement.
    • B — Project fits a shared repository convention, not necessarily organization-wide administration.
    • C — User fits one person's cross-project preference, not policy imposed for everyone.
  9. A developer wants a preference across all personal repositories. Which scope fits first?
    • A. Managed
    • B. User
    • C. Project
    • D. Local
    Answer

    Answer: B — User.

    Reason: User scope is the personal cross-project default choice.

    • A — Managed fits administrator-owned organization policy, not a personal preference.
    • C — Project fits a convention collaborators should share in one repository.
    • D — Local fits one person's preference for one project, narrower than this request.
  10. One repository needs a convention that collaborators should receive through version control. Which scope fits?
    • A. Project
    • B. Local
    • C. User
    • D. Managed
    Answer

    Answer: A — Project.

    Reason: Project scope is the shared repository convention choice when intentional Git sharing is required.

    • B — Local fits untracked project-specific preference for one user, not collaborator distribution.
    • C — User fits one person's defaults across projects, not one repository's team convention.
    • D — Managed fits organization control, broader than a repository-level shared practice.
  11. A generated example claims a session feature exists in another SDK language. What is the sound next action?
    • A. Treat the generated code as proof
    • B. Verify target language, version, documentation, and a controlled test
    • C. Assume every SDK has feature parity
    • D. Infer behavior from a session label
    Answer

    Answer: B — Verify target language, version, documentation, and a controlled test.

    Reason: Session APIs and language parity are version-sensitive implementation claims.

    • A — Generated code fits a hypothesis or starting point, not evidence of target capability.
    • C — Parity could fit a documented supported feature set, but it cannot be assumed from another example.
    • D — A label fits human identification, not proof of SDK semantics or API availability.
  12. A transcript reports a retention duration and storage behavior. How should an author use it?
    • A. State it as permanent current fact
    • B. Treat it as version-sensitive and verify current behavior
    • C. Use it to infer all settings precedence
    • D. Use it to select project scope automatically
    Answer

    Answer: B — Treat it as version-sensitive and verify current behavior.

    Reason: Retention and storage behavior were marked UNVERIFIED and require current product evidence.

    • A — Permanent claims fit stable verified documentation, not transcript-era operational observation.
    • C — Precedence fits scope-resolution evidence, not a retention observation.
    • D — Project scope fits shared repository convention, not a conclusion from storage duration.

Quick recall

Attempt each question before expanding it.

When does resume fit?

Resume fits when one prior conversation must continue with its earlier state, subject to checking compatible workspace and current product behavior.

What does a fork preserve and what remains isolated?

A fork starts from shared earlier history while preserving the source conversation; later branch state is isolated from sibling branches.

How does rewind differ from fork?

Rewind changes the current conversation toward an earlier point and can affect later history. Fork creates a distinct branch while preserving the original.

What does renaming a session change?

It improves human identification among related conversations. It does not by itself establish a change to session history or capability.

Why inspect context after switching sessions?

Context measurements apply to the active session. Another selected or resumed conversation can have different history, category use, and headroom.

When does compact fit?

Compact fits when prior work remains useful but a summarized representation can reduce context use. Verify exact current behavior before relying on it.

When does clear fit, and what is its boundary?

Clear fits a fresh conversation where prior history should not influence the next task. It is not merely terminal-screen clearing; confirm current retention effects before use.

Which setting scope fits organization-wide control?

Managed scope fits organization-controlled policy. Confirm the legal scope for a specific setting in current documentation.

How do user, project, and local scope differ?

User is one person's cross-project default; project is a shared repository convention; local is one user's project-specific untracked preference in this source framing.

What must be checked before resolving a scope conflict?

Identify the intended owner, then verify current precedence and whether the setting is permitted at each candidate scope. Storage location alone is insufficient.

What minimal evidence supports an SDK session-capability claim?

Check the target language and installed version, current documentation, and a controlled test that observes the claimed behavior.

Which session facts remain version-sensitive here?

Command strings, flags, settings file names, precedence details, retention, storage behavior, SDK parity, and capability availability require current verification.
