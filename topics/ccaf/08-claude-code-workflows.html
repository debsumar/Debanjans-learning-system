Claude Code workflows and model use

Choose a capability trade-off, keep harness and application boundaries clear, and verify setup with observed evidence.

In one minute

  • Use a coding harness to gather context, take action, and verify results; an edit is not complete until relevant evidence is checked.
  • Choose a model option by current task complexity, speed need, context need, and planning boundary; do not treat a named option as a permanent product fact.
  • Separate installation and authentication smoke tests from application behavior; a working command does not validate program integration.
  • Keep CLI workflow and SDK application roles distinct; both can support agent work without being interchangeable integration surfaces.
  • Place executable procedure in a skill and keep coordinator guidance light; a description routes or invokes work but does not replace its procedure.

Context, action, and verification

A Claude Code workflow is treated here as a coding-harness loop: gather enough codebase context, take a bounded action, then verify the result. It can accept feedback and repeat when evidence shows the goal remains unmet. Exact commands and product behavior are version-sensitive; the decision rule is not.

  1. Gather task-relevant context before changing work.

    Inspect the request, nearby code, tests, constraints, and existing evidence. Reading everything is not required; sufficient context is bounded by the decision at hand.

  2. Take the smallest action that addresses the observed need.

    Edit, create, invoke a local capability, or ask for clarification according to the task boundary. A proposed change is not yet proof of a correct result.

  3. Verify the result with relevant evidence.

    Use an appropriate check such as a test, output inspection, file evidence, or review against the requested condition. Select evidence that can falsify the change, not only evidence that reports completion.

  4. Use feedback to continue, correct, or stop.

    If verification exposes a gap, return to context with the new evidence. If the requested condition is satisfied, preserve the result and finish.

Choose capability, not a memorized name

Model selection is a task decision: use the option whose currently documented capability trade-off fits the work. A routine, low-risk task may favor responsiveness; difficult reasoning may justify more deliberate capability; a long-lived investigation may prioritize usable context; a plan-first workflow may separate planning from execution.

Task constraintChoice ruleBoundary
Routine bounded coding taskPrefer an option documented as responsive enough for ordinary work.Responsiveness does not prove a result is correct; retain verification.
Difficult or ambiguous reasoningPrefer an option documented for stronger deliberation when the extra effort is justified.Capability does not replace requirements, tests, or review.
Long investigationPrefer an option or workflow with sufficient documented context capacity for needed evidence.More context can still contain irrelevant or stale material; curate it.
Plan before implementationUse a deliberate planning boundary, then execute against the reviewed plan if the current tool supports that workflow.Do not assert a particular mode name, alias, switch, price, or context limit without current documentation.
Common wrong turn

“One named model option is always best for every loop phase.” — Choose by current complexity, speed, context, and planning needs, then verify behavior. Names, aliases, availability, and exact limits are version-sensitive.

Establish which boundary is working

A setup smoke test establishes a narrow fact: installation, authentication, and a minimal local action can be observed. It does not establish that an application integration has correct credentials, permissions, asynchronous control flow, data handling, or tool behavior. Treat exact installer commands, flags, account flows, and settings as current-documentation questions rather than stable study facts.

ConfuseClaude Code is a CLI coding harness for an interactive workflow. An Agent SDK application is program integration that embeds an agent boundary in code. Claude, Code, and SDK can support related work, but a successful CLI smoke test does not prove an SDK application works, and an SDK run does not prove a CLI session is authenticated.
Common wrong turn

“The command launched, so the application behavior is validated.” — A launch or login observation proves only its setup boundary. Validate application behavior separately with its own inputs, output, and evidence.

Keep workflow roles separate

An agentic loop may be used through a coding harness or embedded through an Agent SDK application. The first centers an interactive codebase workflow; the second centers program-owned integration. Their shared vocabulary does not erase their ownership boundary.

ConcernCoding harness workflowProgram integration boundary
Primary ownerA developer directs interactive work against a codebase and reviews evidence.An application owns invocation, inputs, state, and its surrounding behavior.
Useful smoke evidenceObserved local session, authenticated boundary, and a small controlled file or task result.Observed program entrypoint, declared inputs, returned output, and relevant execution evidence.
Failure interpretationSeparate harness setup from repository, task, or verification failure.Separate dependency, application control flow, permission, and tool behavior before judging the integration.
Procedure ownershipA skill description can help direct invocation; its procedure carries operational steps.Coordinator guidance routes or scopes work lightly; it should not duplicate the skill procedure.

Keep the description short enough to identify when a skill applies. Keep the procedure with that skill so execution guidance travels with the capability. Keep coordinator guidance focused on routing, ownership, and boundary conditions rather than copying an entire procedure into a second location.

MCQs

  1. A coding task has unclear failure evidence. What loop action should occur before a broad edit?
    • A. Gather task-relevant code, test, and constraint context
    • B. Apply the largest plausible refactor
    • C. Declare completion from the task description
    • D. Select a faster model option without inspecting evidence
    Answer

    Answer: A — Gather task-relevant code, test, and constraint context.

    Reason: Context gathering establishes the bounded evidence needed to choose and evaluate an action.

    • B — A broad refactor fits when evidence has established a cross-cutting design change, not when the failure remains unclear.
    • C — Declaring completion fits only after relevant verification shows the requested condition is satisfied, not from the description alone.
    • D — Selecting a responsive option fits after a task trade-off is known, not as a substitute for inspecting evidence.
  2. A change was written to disk, but no test or inspection has run. Which loop phase remains incomplete?
    • A. Context gathering
    • B. Action
    • C. Verification
    • D. Feedback intake
    Answer

    Answer: C — Verification.

    Reason: An edit is an action; relevant evidence must still check whether the requested result holds.

    • A — Context gathering fits before an action when the task needs evidence, not the missing post-change check in this stem.
    • B — Action fits when making the change itself, which has already happened here.
    • D — Feedback intake fits when a prior check supplies new information for another loop, not before the first verification.
  3. A task needs careful reasoning about ambiguous requirements and can tolerate more deliberation. What is the best model-selection rule?
    • A. Choose the named option memorized from an old guide
    • B. Choose an option currently documented for stronger deliberation, then verify output
    • C. Always choose the most responsive option
    • D. Skip model choice because tests guarantee reasoning quality
    Answer

    Answer: B — Choose an option currently documented for stronger deliberation, then verify output.

    Reason: Complexity can justify a more deliberate capability trade-off, while verification remains required.

    • A — Historical naming is useful only for locating older notes, not for asserting current availability or capability.
    • C — A responsive option fits routine bounded work when speed is the constraint, not this ambiguity-heavy task.
    • D — Tests fit verification of specified behavior, not replacement of model-choice reasoning for ambiguous requirements.
  4. A workstream must preserve a large amount of relevant evidence across investigation. Which factor should influence model or workflow selection?
    • A. Current documented usable context capacity
    • B. A remembered alias from a prior release
    • C. The color of the terminal theme
    • D. Whether an installer completed once
    Answer

    Answer: A — Current documented usable context capacity.

    Reason: Long investigations need enough usable context for relevant evidence, while still requiring curation.

    • B — An old alias is useful only as a search clue for current documentation, not as evidence of present capability.
    • C — Terminal theme choice fits local readability preferences, not context needs.
    • D — Installation success fits a setup smoke test, not selection for a long investigation.
  5. A developer observes an authenticated local CLI session. What claim is justified without further application testing?
    • A. The application integration has correct control flow
    • B. The SDK has every required permission
    • C. The observed CLI authentication boundary works
    • D. The model output is correct for every task
    Answer

    Answer: C — The observed CLI authentication boundary works.

    Reason: A smoke test supports the narrow setup fact it observed, not broader application or output claims.

    • A — Application control flow is relevant only when the application entrypoint and behavior have been separately exercised.
    • B — SDK permissions are relevant when the program integration declares and uses them, not from a CLI session alone.
    • D — Output correctness is relevant after task-specific verification, not after authentication.
  6. A reusable capability needs direct invocation and repeatable execution steps. Where should its description and procedure live?
    • A. Put both only in coordinator guidance
    • B. Use a skill description for invocation and keep procedure in the skill
    • C. Put the procedure only in a terminal transcript
    • D. Store the description in a test assertion and omit procedure
    Answer

    Answer: B — Use a skill description for invocation and keep procedure in the skill.

    Reason: The description identifies or invokes the capability; the skill owns its executable operational guidance.

    • A — Coordinator guidance fits light routing and ownership direction, not duplicated full procedure detail.
    • C — A terminal transcript fits evidence of one run, not reusable operational procedure ownership.
    • D — A test assertion fits checking a condition, not describing when a skill applies or how it operates.
  7. A coordinator document repeats every implementation step from a skill. What boundary-preserving revision is best?
    • A. Expand the duplicate until it becomes the only procedure
    • B. Remove the skill description because coordinators route work
    • C. Keep a light routing pointer and retain detailed procedure in the skill
    • D. Move all procedure into a model-selection note
    Answer

    Answer: C — Keep a light routing pointer and retain detailed procedure in the skill.

    Reason: Coordinator guidance should direct work without creating a competing procedure copy.

    • A — Duplication fits only when independently maintained copies are explicitly required, not for one authoritative procedure.
    • B — Removing the description fits only when direct invocation is not needed, not when the capability must be discoverable.
    • D — Model-selection notes fit capability trade-offs, not procedure ownership.

Quick recall

Attempt each question before expanding it.

State the coding-harness loop and its completion boundary.

Gather task-relevant context, take a bounded action, verify with relevant evidence, then finish only when the requested condition is satisfied; otherwise use feedback for another loop.

Why is a written edit not sufficient evidence of task completion?

Writing is an action, not verification. A relevant test, inspection, artifact check, or review must establish whether the requested condition actually holds.

Which four constraints guide a model-option choice without relying on a named current product fact?

Task complexity, needed responsiveness, usable context need, and whether a reviewed planning boundary should be separated from execution. Validate named options and behavior against current documentation.

What remains necessary after selecting an option for difficult reasoning?

Requirements, focused context, verification evidence, and review remain necessary. A capability choice changes a trade-off; it does not guarantee a correct result.

Contrast a setup smoke test with application behavior validation.

A smoke test establishes a narrow observed setup fact such as installation, authentication, or a minimal local action. Application validation separately exercises its entrypoint, inputs, permissions, control flow, output, and relevant evidence.

Why must a CLI workflow and program integration be tested independently?

They have different ownership boundaries. A successful CLI session does not prove program credentials, asynchronous flow, permissions, data handling, or tool behavior; a successful program run does not prove the CLI session boundary.

Where do skill description, procedure, and coordinator guidance belong?

A skill description identifies or supports invocation of the capability; the skill contains its operational procedure; coordinator guidance stays light and covers routing, ownership, and boundaries rather than duplicating the procedure.
