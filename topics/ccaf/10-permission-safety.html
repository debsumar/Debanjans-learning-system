Permissions, sandboxing, and safe execution

Authorize narrowly, test every viable route, and treat prompt skipping as exceptional risk.

Domain 3Claude Code configuration and workflowsWeight unverified
In one minuteSkills in scopeRule resolutionSandbox boundaryModes and matchersBypass riskMCQsQuick recall

In one minute

  • Grant the least privilege needed for stated work; a familiar tool name is not a safe substitute for a narrow matcher.
  • Test deny, ask, and allow behavior against alternate tool paths; blocking one command does not prove information or action is blocked.
  • Keep permission authorization separate from a Bash sandbox; neither layer alone defines every tool or network boundary.
  • Select an interaction mode for task risk and review need; mode labels and exact behavior require current-product verification.
  • Do not normalize bypassing prompts; use it only for low-risk, well-scoped work in a disposable environment with acceptable failure.

Resolve rules, then test actual reachability

A permission rule authorizes, asks about, or denies a tool or command under a stated matcher scope. Least privilege begins with the smallest useful tool, path, command, domain, or parameter scope; it does not begin by granting a broad tool merely because a task sounds routine.

The transcript describes restrictive resolution as deny, then ask, then allow. Treat that ordering, rule syntax, and live-reload behavior as version-sensitive configuration facts: inspect effective behavior in the target environment rather than assuming a remembered rule wins.

Policy completeness needs route analysis. A denied shell command may not prevent a dedicated search, listing, read, edit, or delegated tool from reaching related material. Identify the resource, enumerate feasible tool paths, constrain each relevant path, then perform harmless execution tests in a throwaway workspace.

Common wrong turn

“Denying one familiar command proves the resource is protected.” — A policy controls only matched actions. Another available tool can offer an alternate route to the same information or effect.

Authorization and execution containment differ

A sandbox is an execution boundary for Bash-tool host access in the transcript-described flow. A permission rule answers whether a requested action is authorized; a sandbox constrains how Bash executes if it is invoked. These controls can reinforce each other, but neither should be described as an all-tool security guarantee.

Choose interaction mode and matcher scope deliberately

Permission modes set an interaction posture: a workflow can request review, accept a limited class of changes, deny actions unless explicitly approved, or skip prompts. Transcript-described mode names, keyboard toggles, and exact launch settings are UNVERIFIED product details; choose from the safety property required, then verify the current configuration surface.

Matchers are executable policy, not comments. A command pattern can change meaning with argument boundaries or spaces; a path pattern can distinguish project-relative scope from a broader root scope. Keep patterns minimal, test matching and nonmatching examples, and avoid claiming a complete syntax specification from the transcript.

ConfuseAsk preserves a review decision for an unapproved action. Bypass skips prompts. Ask can lead to approval or denial; bypass removes that decision point and therefore needs a much stronger environment boundary.
Common wrong turn

“A mode that removes prompts is a normal productivity default.” — Prompt removal also removes human review. Use the narrowest permission mode that serves the task, and verify actual mode behavior before relying on it.

Worked scenario: unattended cleanup versus unknown execution

A team wants unattended cleanup in a repository. The safe question is not how to silence prompts; it is whether work is known, low-risk, narrow, reversible, and isolated. A predefined cleanup over an empty throwaway directory can justify carefully tested rules. An unfamiliar command that can download or execute code does not become safe because a prompt delays it.

  1. State the task, affected paths, commands, data, and expected result.

    Reject vague scope. If the action may affect sensitive data, credentials, production systems, or unknown downloaded code, keep human review and do not use bypass as a routine solution.

  2. Grant the minimum tested permission and enumerate alternate routes.

    Use narrow matchers and test allowed, asked, denied, and alternate-tool behavior with harmless samples.

  3. Run in a disposable environment with least-privilege credentials.

    A VM or development container limits blast radius. It does not excuse broad access, persistent secrets, or unreviewed service permissions.

  4. Verify durable results and remove the temporary environment when finished.

    Inspect changed artifacts and logs, revoke temporary access where applicable, and terminate or reset the disposable environment to limit residual cost and exposure.

The transcript demonstrates that permissive settings can let an agent alter its protection state after a blocked attempt. Treat that as a security warning: deny rules and sandboxing require reviewable configuration, defense in depth, and an environment whose loss is acceptable. Do not use permission-skipping as a fix for a failed command.

Common wrong turn

“Sandboxing makes prompt bypass safe on a primary workstation.” — Sandboxing is an additional control with a defined boundary. Bypass removes approval review; unknown commands, credentials, and alternate paths can still create unacceptable risk.

MCQs

  1. A policy denies a shell command that reads a report, but the agent still locates report content through another dedicated search capability. What is the best conclusion?
    • A. The deny rule is ineffective and should be removed
    • B. The shell denial proves all report access is blocked
    • C. The policy must assess and constrain alternate tool paths
    • D. A broad allow rule should replace the denial
    Answer

    Answer: C — The policy must assess and constrain alternate tool paths.

    Reason: A rule governs matched actions; complete resource protection requires evaluating other tools that can reach the same information.

    • A — Removing a rule is appropriate when it conflicts with a justified workflow, not when it exposed an omitted route.
    • B — A shell denial is sufficient only when no other available tool can access the resource, which this scenario disproves.
    • D — A broad allow is appropriate only for deliberately accepted broad access, not to repair incomplete restrictive coverage.
  2. A task has one matching deny rule and one matching allow rule. What should an operator do before relying on a predicted result?
    • A. Assume allow wins because work was requested
    • B. Assume remembered precedence is stable everywhere
    • C. Test effective rule resolution in the target configuration
    • D. Use a prompt-skipping mode to avoid the conflict
    Answer

    Answer: C — Test effective rule resolution in the target configuration.

    Reason: The transcript describes restrictive ordering, but precedence and syntax are configuration- and version-sensitive facts that require empirical verification.

    • A — Allow is appropriate only when effective policy resolves to authorization, not merely because an action is desired.
    • B — Remembered precedence is useful as a hypothesis, not as evidence for a target environment.
    • D — Prompt skipping is appropriate only for exceptional, isolated, low-risk work; it does not diagnose policy resolution.
  3. A Bash action is authorized by a permission rule but fails because its execution environment cannot provide required host access. Which control explains the failure?
    • A. Permission authorization
    • B. Bash sandbox boundary
    • C. Tool matcher scope
    • D. A user approval prompt
    Answer

    Answer: B — Bash sandbox boundary.

    Reason: Authorization answers whether an action may proceed; the Bash sandbox constrains how Bash executes on the host.

    • A — Permission authorization is correct when a rule permits, asks about, or denies the requested action, not when execution containment fails afterward.
    • C — Matcher scope is correct when determining which action a rule covers, not when authorized Bash lacks environment access.
    • D — A user prompt is correct when review is required before authorization, not when an already authorized execution boundary blocks access.
  4. A team claims its Bash sandbox protects every tool in an agent workflow. Which correction is most accurate?
    • A. The sandbox is a Bash execution boundary, not an all-tool guarantee
    • B. The sandbox replaces permission rules for every action
    • C. The sandbox automatically denies all network-capable tools
    • D. The sandbox makes a disposable host unnecessary
    Answer

    Answer: A — The sandbox is a Bash execution boundary, not an all-tool guarantee.

    Reason: The described sandbox constrains Bash-tool execution and remains separate from authorization and other tool boundaries.

    • B — Replacing permission rules would fit only a system designed with one universal authorization boundary, which this distinction rejects.
    • C — A network denial is correct only when an explicit applicable control enforces it; a Bash sandbox alone does not establish that claim.
    • D — A disposable host is still appropriate when reducing acceptable blast radius for risky work; sandboxing is additive, not a replacement.
  5. A repository analysis must not change files or execute unreviewed actions until scope is understood. Which permission posture best fits?
    • A. Review-oriented planning posture
    • B. Prompt-skipping bypass posture
    • C. Broad edit and command acceptance
    • D. Unrestricted root-path matcher
    Answer

    Answer: A — Review-oriented planning posture.

    Reason: Initial analysis needs human review and bounded scope before mutation or command execution is permitted.

    • B — Prompt-skipping bypass is appropriate only for exceptional low-risk, isolated automation, not unknown repository analysis.
    • C — Broad acceptance is appropriate only after a task and narrow authority have been reviewed, not before scope is understood.
    • D — A root-path matcher is appropriate only when broad root scope is explicitly justified; it violates the stated least-privilege boundary.
  6. A path matcher unexpectedly includes files outside the intended project area. What is the safest next action?
    • A. Keep it because the task may need future files
    • B. Narrow the matcher and test matching and nonmatching samples
    • C. Replace it with a bypass setting
    • D. Treat path syntax as harmless documentation
    Answer

    Answer: B — Narrow the matcher and test matching and nonmatching samples.

    Reason: Matchers are executable policy; least privilege requires a minimal scope validated against both intended and excluded cases.

    • A — Future flexibility is appropriate only when broader access has been consciously accepted, not when it exceeds current task scope.
    • C — Bypass is appropriate only under exceptional isolated controls; it cannot make an overbroad matcher safe.
    • D — Documentation is appropriate for explaining policy, but matcher behavior must be tested because it affects authorization.
  7. An unattended task may run an unfamiliar command that could download and execute code on a workstation holding credentials. What is the safest decision?
    • A. Skip prompts to prevent queue delays
    • B. Run it in bypass mode because a sandbox exists
    • C. Keep approval review and avoid routine bypass on that host
    • D. Grant broad permissions once so future tasks are faster
    Answer

    Answer: C — Keep approval review and avoid routine bypass on that host.

    Reason: Unknown code and sensitive credentials create unacceptable risk; bypass removes a human review boundary and sandboxing is not a complete guarantee.

    • A — Skipping prompts is appropriate only for well-scoped, low-risk work in an acceptable disposable environment, not for this unknown command.
    • B — Sandbox use is appropriate as an additional control, but it does not justify bypass on a credential-bearing workstation.
    • D — Broad permissions are appropriate only where broad authority is intentionally required and controlled, not as a speed optimization for uncertain work.

Quick recall

Attempt each question before expanding it.

How should a policy test distinguish a denied familiar tool from protected information?

Map the resource to every feasible tool path, test harmless denied and alternate paths, then constrain each relevant path. A denied command alone does not prove information is unreachable.

What rule-resolution claim from a transcript should be treated as a testable configuration fact?

The transcript describes deny, then ask, then allow as restrictive resolution. Verify current precedence, syntax, and effective behavior in the target environment before relying on it.

Contrast permission authorization with a Bash sandbox.

Permission authorization decides whether a matched action may proceed. A Bash sandbox constrains Bash execution on its host. They are complementary controls with different boundaries.

Why does a Bash sandbox not establish all-tool protection?

Its described boundary is Bash execution. Other tools, authorization decisions, network controls, credentials, and alternate paths require their own applicable controls and verification.

How do you choose an interaction mode without relying on unverified product labels?

Choose the required safety property: review for uncertain work, narrow permission for known edits, ask or deny for unapproved actions, and no prompt skipping unless exceptional low-risk work is isolated. Then verify current product behavior.

Why must command and path matchers receive matching and nonmatching tests?

They are executable policy. Argument boundaries, spaces, relative paths, and broader root scope can change what matches, so test intended actions and exclusions in a harmless workspace.

What controls make unattended work less risky without claiming it is safe by default?

Use known, narrow, reversible work; least-privilege rules and credentials; alternate-path testing; a disposable VM or container; durable result inspection; and cleanup of temporary access and environments. Keep human approval for unknown or sensitive work.
