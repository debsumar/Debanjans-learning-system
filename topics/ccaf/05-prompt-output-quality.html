Prompt, output, and review quality

Constrain useful work, validate its shape and meaning, then review it with evidence.

In one minute

Skills in scope

This provisional mapping remains subject to the official guide when it is published.

  • Use positive, negative, and scored examples to constrain output without claiming truth guarantees.
  • Write specific, bounded instructions that reduce false positives and review burden.
  • Separate schema/syntax validation from semantic, business-rule, and human quality validation.
  • Design independent review and confidence-calibrated human review using segmented evidence.

Examples constrain output, not truth

A few-shot prompt can show the shape, tone, and decision boundary wanted from an output. The transcript reports that positive examples, negative examples, and scored examples can make formatting more consistent and reduce hallucinations. They supply target evidence; they do not prove that a generated claim is true.

Common wrong turn

“A strong example makes every generated claim reliable.” — Examples constrain requested output and may reduce hallucinations, but factual, business-rule, and human quality checks remain separate work.

Choose boundaries before broad work

Specific instructions name the target, relevant location or input, expected behavior, and boundary. A vague request can widen search and action, create false positives, consume more compute, and leave a reviewer with unrelated changes. A structured output request can make downstream handling clearer, but its requested fields still need validation.

Constraint to choice: if task shape is known, specify the input, target, expected result, exclusions, and acceptance criteria before execution. If information needed to set that scope is missing, clarify the task rather than allowing an unconstrained audit. If work is intentionally exploratory, state the broad goal and a review boundary instead of disguising exploration as a precise defect request.

Quality criteria should be concrete enough to inspect: coverage axes, source or evidence requirements, requested detail, and a stopping condition. Logging a quality score does not by itself enforce or measure those criteria. Persisting useful findings after a batch reduces the loss caused by interruption, while still requiring a later quality check.

Validate structure, meaning, and review evidence

Validation has layers. Schema and syntax checks ask whether output matches a required shape. Semantic checks ask whether values are correct or coherent. Business-rule checks ask whether values satisfy task policy. Human review can assess quality, ambiguity, and risk that automated checks do not establish.

  1. State required fields, allowed values, and quality rules.

    Examples and explicit criteria give the generator and validator a target. A schema constrains structure, while semantic and business rules remain separate checks.

  2. Validate the submitted output at the required layer.

    Return a precise failure, such as a missing required field or a violated business rule, rather than a generic rejection.

  3. Provide the specific error for a bounded correction attempt.

    A remediation loop can append the failure details and request a revised output, but it needs a maximum attempt count and a terminal path.

  4. Stop on pass, cap, or absent required source information.

    Repeated correction cannot supply a fact that the source material does not contain; stop or escalate instead of blind regeneration.

Flow: requirement, examples and criteria, validation, then independent review. A failure returns specific feedback for bounded remediation; a pass still proceeds to appropriate review evidence.

ConfuseSchema validation checks structure and syntax; semantic validation checks meaning, factual or business correctness, and other quality conditions. A schema-valid record can still be semantically wrong.
Common wrong turn

“Valid JSON proves a correct decision.” — A valid shape can satisfy schema and syntax while its values fail semantic, business-rule, or human quality validation.

Worked scenario: review a fielded extraction

A generator extracts fields from varied documents and reports a single aggregate accuracy value. The team instead sends the artifact to an independent reviewer in a fresh context, records field-level confidence, and samples each document category. A low-confidence field can be routed for human review even when other fields in the same document appear strong.

Independent review separates the reviewer from the generator conversation history. Same-conversation self review retains earlier choices and can anchor the evaluator to its own output. A fresh context, separate agent, or another model can reduce that self-review anchoring; none alone proves the result correct.

Evidence viewWhat it revealsReview use

Track reviewer confirmation, edits, and deferrals with the field and document category. This creates evidence for calibration: confidence is an item signal, whereas measured accuracy compares output with reviewed or expected values. Do not treat low confidence as proof of falsehood or high confidence as proof of correctness.

MCQs

  1. A team needs a consistent incident-summary shape and wants to show both acceptable and unacceptable wording. What prompt evidence best fits?
    • A. Positive and negative examples
    • B. A larger context window only
    • C. A generic request for a better summary
    • D. A final human review with no examples
    Answer

    Answer: A — Positive and negative examples.

    Reason: Desired and undesired examples constrain output shape and boundaries while leaving factual validation separate.

    • B — A larger context window is correct when addressing an input-capacity problem, not a need to demonstrate accepted and rejected output forms.
    • C — A generic request is correct when the work is an exploratory rewrite, not a task requiring consistent explicit output evidence.
    • D — Human review is correct when making a later quality-control decision, not when initially constraining generated format.
  2. A scored example matches the requested answer format. What claim remains unsupported?
    • A. The format preference is clearer
    • B. The new generated claim is true
    • C. Output consistency may improve
    • D. The example can guide a quality preference
    Answer

    Answer: B — The new generated claim is true.

    Reason: Scored examples constrain preferences and formatting; they do not verify the factual truth of a new answer.

    • A — Clearer format preference is correct when scored examples distinguish preferred output patterns.
    • C — Improved consistency is correct when examples supply a reported formatting benefit, not a truth guarantee.
    • D — Guiding a quality preference is correct when examples supply comparative scoring evidence.
  3. An agent receives the instruction “fix the login bug” and changes unrelated files. Which revision most directly reduces false positives?
    • A. Ask for every defect in the repository
    • B. Specify target behavior, affected area, exclusions, and acceptance criteria
    • C. Add more examples without identifying the target
    • D. Require a longer final explanation
    Answer

    Answer: B — Specify target behavior, affected area, exclusions, and acceptance criteria.

    Reason: Bounded instructions narrow relevant work and make review against an expected result possible.

    • A — A repository-wide audit is correct when deliberately exploring all defects, not when one login behavior is the intended scope.
    • C — More examples are correct when output form needs demonstration, not when the task target itself remains unspecified.
    • D — A longer explanation is correct when reviewers need narrative detail, not when the agent lacks a work boundary.
  4. A task request omits the affected system and expected behavior. What should occur before a supposedly precise repair?
    • A. Clarify the missing scope
    • B. Search every file for likely defects
    • C. Accept any changed file as success
    • D. Skip review because requirements are incomplete
    Answer

    Answer: A — Clarify the missing scope.

    Reason: A precise repair needs a target and acceptance boundary; otherwise broad work can create unrelated candidates.

    • B — Broad search is correct when used for an explicitly stated exploratory audit, not for an underspecified repair request.
    • C — Any changed file is correct only when used for a task that asks for unconstrained experimentation, not for a reviewable repair.
    • D — Skipping review is correct only when no output is used, not when incomplete requirements increase the need for a clear boundary.
  5. A record includes all required keys and valid allowed values, but assigns the wrong customer category under policy. Which validation found the defect?
    • A. Schema validation
    • B. Syntax validation
    • C. Semantic or business-rule validation
    • D. Whitespace normalization
    Answer

    Answer: C — Semantic or business-rule validation.

    Reason: The record has valid structure but incorrect meaning or policy treatment.

    • A — Schema validation is correct when required structure, types, or allowed values are violated, not when a structurally valid category is wrong.
    • B — Syntax validation is correct when encoding or parse form is invalid, not when parsed values fail policy.
    • D — Whitespace normalization is correct when formatting spaces cause a comparison issue, not when category meaning is incorrect.
  6. A validator rejects an output because one required field is missing. Which remediation response best supports a bounded retry?
    • A. Return the specific missing-field error to the next attempt
    • B. Regenerate blindly until a cap is reached
    • C. Mark the output semantically correct
    • D. Treat the missing field as a human approval
    Answer

    Answer: A — Return the specific missing-field error to the next attempt.

    Reason: Precise validation feedback gives remediation a concrete correction target and supports a capped loop.

    • B — Blind regeneration is correct only when used for a deliberately random exploration, not for remediation that needs known failure details.
    • C — Semantic correctness is correct when established after meaning and policy checks pass, not when a required structural field is absent.
    • D — Human approval is correct when a reviewer must decide ambiguous content, not as a substitute for an omitted required field.
  7. A generator approves its own output after reading the same long conversation that produced it. Which review change most directly reduces anchoring risk?
    • A. Ask the generator again in the same conversation
    • B. Use an independent reviewer with a fresh context
    • C. Convert the output to valid JSON
    • D. Increase the aggregate accuracy target
    Answer

    Answer: B — Use an independent reviewer with a fresh context.

    Reason: Fresh review lacks the generator conversation history that can anchor same-context self review.

    • A — Another self review is correct when used for quick author revision, not for independent quality control without retained generation history.
    • C — Valid JSON is correct when downstream syntax needs a contract, not when review bias is the issue.
    • D — An aggregate target is correct when used for a reporting goal, not for separating reviewer context from generator history.
  8. A system reports high overall accuracy but fails frequently for one document type. Which evidence view exposes the weakness?
    • A. Aggregate accuracy only
    • B. Segmented accuracy by document type and field
    • C. One high-confidence sample
    • D. A schema-valid output count
    Answer

    Answer: B — Segmented accuracy by document type and field.

    Reason: Segmentation reveals quality variation that a single aggregate can conceal.

    • A — Aggregate accuracy is correct when used for a concise overall summary, not for locating a category-specific weakness.
    • C — One high-confidence sample is correct when used for inspecting an individual item, not for measuring performance across categories.
    • D — A schema-valid count is correct when used for structural compliance, not for detecting accuracy variation by category.
  9. One document has high confidence for a date field and low confidence for a vendor field. What review routing fits?
    • A. Auto-approve the whole document from the date confidence
    • B. Route the low-confidence vendor field for human review
    • C. Reject every field because one is uncertain
    • D. Treat confidence as measured accuracy
    Answer

    Answer: B — Route the low-confidence vendor field for human review.

    Reason: Field-level confidence supports targeted review; confidence is a routing signal rather than proof of correctness.

    • A — Document-level auto-approval is correct when policy accepts document-level evidence, not when field confidences differ materially.
    • C — Rejecting every field is correct when a document is globally unusable, not when one uncertain field can receive targeted review.
    • D — Measured accuracy is correct when established after comparison with reviewed or expected values, not from a confidence signal alone.

Quick recall

Attempt each question before expanding it.

How do positive, negative, and scored examples differ?

Positive examples show acceptable output, negative examples bound unwanted output, and scored examples add comparative quality preference. All can constrain a request, but none proves factual truth.

What is the boundary on the claim that examples reduce hallucinations?

Examples can improve consistency and reduce hallucinations according to the transcript, but they do not eliminate hallucinations or validate a new claim against evidence.

Which details turn a vague repair request into bounded instruction?

Name the target or affected area, input or location, expected behavior, exclusions, and acceptance criteria. Clarify missing scope before claiming a precise repair.

Why does prompt specificity reduce review burden?

Specific boundaries narrow search and action, reduce unrelated false positives, and give reviewers an expected result and exclusions against which to assess work.

Contrast schema or syntax validation with semantic and business-rule validation.

Schema and syntax validation check required structure, types, allowed values, or parse form. Semantic and business-rule validation check whether the values mean the right thing and satisfy task policy.

What makes a validation-retry loop remediation rather than blind regeneration?

The validator returns precise failures to the next attempt, attempts are capped, and the loop stops or escalates when required source information is absent or the cap is reached.

Why can same-conversation self review be biased?

It retains the generator history, reasoning, and choices, which can anchor judgment. An independent reviewer uses a fresh context but still needs evidence and review criteria.

Why can aggregate accuracy hide a quality problem?

A single aggregate can mask poor performance for a document type or field. Segment results and use stratified sampling so each category contributes evidence.

How should field-level confidence affect human review?

Use it as a routing signal for confirmation, editing, or deferral of uncertain fields. Record reviewed outcomes by field and document category; confidence alone is not measured accuracy.
