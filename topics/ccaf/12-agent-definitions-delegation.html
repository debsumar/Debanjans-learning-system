Agent definitions and delegation

Define a bounded agent surface, verify version-sensitive claims, and separate work ownership before delegation grows.

Skills in scope

This provisional mapping remains subject to the official guide when it is published.

  • Define agent identity, description, prompt, model, turns, and allow/disallow tool controls.
  • Validate SDK field and terminology claims against target language and version.
  • Plan parallel-safe delegation without inferring scheduling or internal-loop visibility.
  • Refactor coordinator responsibilities into testable, human-readable ownership boundaries.

Definition surface: identity, routing, and boundaries

An agent definition is a pre-message blueprint: it states who the agent is, what work it should be considered for, its stable instructions, and the capability boundary around that work. It is not the request-time user message and not proof of a particular SDK object shape.

Treat both a distinctive identity or name and task-specific description wording as routing-sensitive. Inspect both when an agent is not selected as expected; use the description to state what task or condition makes invocation fit. Treat the prompt as stable system-level instruction for the definition. A model choice, a turn limit, an allowed-tool set, and an explicit disallowed-tool control can express further operating limits, but the transcript marks their exact field names, types, language parity, and target-SDK selection behavior UNVERIFIED.

Use allowed tools to grant only capabilities needed for the bounded task. If the target implementation supports an explicit disallow control, use it to record a prohibited capability as well. Neither a tool name nor a generated code example establishes that the control exists in the target language and version.

Common wrong turn

“A generic description is enough because the prompt contains the real behavior.” — The description is the routing surface. Vague routing language makes it harder to select the right bounded agent even when its prompt is strong.

Validate claims in the target SDK

SDK documentation, generated examples, older tutorials, and another language binding are evidence to investigate, not a transferable configuration contract. The transcript specifically warns that Python and TypeScript surfaces may differ or change at different times. Record the target language and version, inspect its current primary documentation, make a small test, and preserve observed behavior before relying on a field or terminology claim.

Target-SDK and version caveat: One transcript-era observation used historical task terminology where newer material used agent. Treat that as a version-sensitive naming observation, not timeless API equivalence. In that observed target SDK and version, lifecycle messages included task-start, task-progress, and task-notification; validate their names, availability, and semantics in the target implementation.

Plan parallel-safe work without scheduling claims

Parallel-safe planning begins with task dependency, not with an assumed runtime. Split research axes only when each can answer its bounded question without an earlier agent result and without competing writes to the same state. State the task, inputs, expected result shape, tool scope, and merge rule for every axis before requesting concurrent work.

A coordinator instruction can request that independent axes be attempted without waiting between them. Treat that as an intent to validate, not as a guarantee about scheduler behavior, completion order, internal loops, or streaming visibility. Inspect target-version run evidence and keep permissions least-scope while doing so.

Target-SDK and version caveat: In one transcript-era target SDK and runtime, spawning one sub-agent normally blocked its parent until that sub-agent reported back. This is not a universal parallelism rule; validate parent blocking, scheduling, and emitted lifecycle behavior in the target version.

Direct-SDK versus internal-MCP boundary: One transcript-era port replaced direct SDK tool handling with decorated functions and an SDK MCP server used internally to pass tools. Treat that internal-MCP arrangement as target-SDK and version dependent, not evidence of a remote MCP deployment or a guaranteed porting pattern. Validate the target tool, decorator, and server boundary before adopting it.

Common wrong turn

“Several defined agents automatically execute in parallel and expose their progress.” — Definitions describe boundaries. Scheduling and internal observability are separate, version-sensitive runtime questions that require evidence.

Refactor responsibility into testable ownership

When one coordinator entry point mixes prompt text, agent definitions, tool policy, partition selection, result formatting, and logging, its flow becomes difficult for a human to inspect or test. Separate named ownership boundaries with explicit inputs and outputs. The transcript refactor used possible destinations such as prompt files, individual tool files in a tools directory, partition and logger helpers in library files, a coverage-report helper, and data artifacts in a data directory. A function, module, or stateless domain grouping can fit when it clarifies responsibility; these destinations are examples, not source-independent requirements.

Defer a shorthand redesign, including a change to tool-definition representation, pending target-SDK validation. A planned SDK port does not establish that a shorter form exists or preserves the intended boundary.

MCQs

  1. An evidence-review agent is not selected for a request it was designed to handle. Which definition surfaces should the team examine first?
    • A. The agent name and its task-specific description wording
    • B. The maximum number of turns
    • C. The final report formatting template
    • D. The caller display label without its routing-sensitive name or description
    Answer

    Answer: A — The agent name and its task-specific description wording.

    Reason: Both the name and description are routing-sensitive; inspect both, especially task-specific description wording, when selection misses.

    • B — A turn limit can fit bounding work after an agent is running, but it does not describe when the agent should be considered.
    • C — A report template can fit shaping returned output, but it does not define routing into the agent.
    • D — A caller display label can fit human recognition, but it does not replace inspection of the agent name and task-specific description that affect routing.
  2. A team wants stable rules for an agent while keeping a customer question specific to one run. Which split best preserves the boundary?
    • A. Put both stable rules and the customer question only in the agent description
    • B. Put stable behavior in the definition prompt and pass the customer question at request time
    • C. Put the customer question in a model name and omit instructions
    • D. Put all stable rules in a tool result after the agent acts
    Answer

    Answer: B — Put stable behavior in the definition prompt and pass the customer question at request time.

    Reason: The definition prompt is the stable instruction boundary; request-time content remains the current task input.

    • A — A description is correct for routing and invocation fit, not as the sole replacement for stable instruction and current request content.
    • C — Model selection can fit choosing a model option, but it does not carry task instruction or customer input.
    • D — A tool result is correct after a requested action produces output, not for establishing instructions before work begins.
  3. A generated example uses an agent configuration option that is absent from the target language documentation. What is the defensible next action?
    • A. Copy the option because related SDKs should stay identical
    • B. Replace it with a guessed field name from an older tutorial
    • C. Verify target language and version documentation, then run a focused behavior test
    • D. Treat the generated example as proof that the option is deprecated everywhere
    Answer

    Answer: C — Verify target language and version documentation, then run a focused behavior test.

    Reason: SDK field names, terminology, and availability are version-sensitive and can differ across language bindings.

    • A — Copying can fit only after target-version parity is documented and tested; similarity alone is not evidence.
    • B — An older tutorial can provide a candidate to investigate, but guessing a field cannot establish current support.
    • D — Deprecation can be concluded only from relevant target-version evidence, not from one missing documentation entry.
  4. A research agent needs source search but must not modify a production record. Which design best applies tool controls?
    • A. Grant every available tool so the agent can recover from surprises
    • B. Grant task-required search capability and use an explicit disallow boundary if the target SDK supports it
    • C. Omit all tool boundaries because the prompt says not to edit
    • D. Copy another language's control syntax without testing it
    Answer

    Answer: B — Grant task-required search capability and use an explicit disallow boundary if the target SDK supports it.

    Reason: Least-scope capability plus a validated prohibition boundary limits the definition to the stated task.

    • A — Broad access can fit a genuinely cross-domain administrator task, but it violates this narrow research-only boundary.
    • C — Prompt-only guidance can express intent, but it does not replace available capability controls for a prohibited action.
    • D — Cross-language syntax can be a research clue, but it is not safe configuration until target support is verified.
  5. Three source axes can be researched from the same static brief, have no shared write target, and will later be deduplicated. What plan is justified?
    • A. Mark them independent, state a merge rule, and request concurrent work without claiming scheduler behavior
    • B. Declare them parallel and conclude each internal agent loop will be visible
    • C. Make each axis wait for the preceding axis despite no dependency
    • D. Give each axis unrestricted permissions so timing cannot block it
    Answer

    Answer: A — Mark them independent, state a merge rule, and request concurrent work without claiming scheduler behavior.

    Reason: The inputs and write boundaries support a parallel-safe plan, while actual scheduling and internal visibility still require runtime evidence.

    • B — Visible internal loops can fit an SDK with documented instrumentation, but independence alone does not prove that capability.
    • C — Sequential order fits when a later task needs an earlier result; the stem explicitly removes that dependency.
    • D — Broad permissions can fit an explicitly approved administrator task, but they do not establish independence and violate least privilege here.
  6. A coordinator file mixes prompts, capability policy, delegation planning, result synthesis, and logging. Which refactor most improves testability without silently changing its purpose?
    • A. Keep one large routine and add comments around each conditional
    • B. Extract named ownership units with explicit inputs and outputs, then run and inspect preserved artifacts
    • C. Move all logic into one generated prompt so code no longer needs tests
    • D. Rename the file and assume its behavior remains intact
    Answer

    Answer: B — Extract named ownership units with explicit inputs and outputs, then run and inspect preserved artifacts.

    Reason: Clear boundaries create test seams and human-readable flow; runtime evidence checks that the refactor preserved intended behavior.

    • A — Comments can help a small stable routine, but they do not isolate mixed concerns into independently testable ownership boundaries.
    • C — A prompt can contain instructions, but it cannot replace code-level ownership, capability policy, and behavior validation.
    • D — Renaming can fit organizing files, but it supplies no separation or evidence that behavior survived extraction.

Quick recall

Attempt each question before expanding it.

What belongs in an agent-definition surface, and what qualification applies to exact SDK fields?

Define identity, routing description, stable prompt, model choice, turn limit, allowed tools, and any disallow control supported by the target implementation. Exact field names, types, and availability require target language and version validation.

How does an agent description differ from a skill procedure?

An agent description states routing or invocation fit: when the agent may be useful. A skill procedure gives executable steps for doing work. One does not substitute for the other.

Why cannot a TypeScript example alone prove a Python agent configuration?

Language bindings and releases can expose different names, types, terminology, or capabilities. Inspect target-version primary documentation and run a focused test before relying on the configuration.

What makes a delegation axis parallel-safe at planning time?

It has all needed inputs without a prior agent result, no conflicting shared write or ordering constraint, bounded permissions, and a stated rule for merging or comparing its result with the others.

What must not be inferred merely because a plan requests concurrent agent work?

Do not infer actual scheduler behavior, completion order, visibility into each internal loop, or streaming progress. Verify those runtime properties in the target version with run evidence.

How does an ownership-boundary refactor become testable rather than cosmetic?

Give each concern a named owner with explicit inputs and outputs, test the resulting seams, run the preserved workflow, and inspect logs or reports that show behavior and artifacts still meet the intended boundary.
